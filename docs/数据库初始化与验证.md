# 数据库初始化与验证

数据库保留全量初始化基线、初始化数据和已有库升级所需的增量脚本。结构变更必须提供可执行的增量脚本；日常开发尽量不修改全量初始化 SQL，由用户在选定时间节点统一合并此前增量。此前清理历史 SQL 仅针对已整理的旧脚本，后续结构变更仍须提供增量。后端、Web、Mobile 和 Query 使用当前契约一起更新；应用不保留旧接口兼容分支。

## 初始化

1. 在空库执行 `sql/1_init_table/2026-08-18_init_all_tables.sql`。
2. 依次执行 `sql/migrations/2026-10-28_01_asset_purchase_source.sql`、`2026-10-28_02_unify_common_fields.sql`、`2026-10-28_03_schema_alignment.sql`、`2026-10-28_04_schema_comments.sql`。当前基线已包含 `00` 空值/注释变更；`01` 会保留已存在的三项来源字段并补齐另外两项，不能因基线已有部分字段而跳过。
3. 执行 `sql/menu/2_ini_data/2_menu.sql` 建立基础菜单。
4. 按文件名顺序执行 `sql/2_ini_data/*.sql`，再执行 `sql/menu/2_ini_data/202*.sql`。

全量 SQL 描述最近一次合并的结构，作为空库初始化基线；当前最终结构由该基线和后续尚未合并的增量共同定义。修改表时提供增量脚本，同步实体、Mapper、请求/响应、两端调用和表结构文档。用户统一合并时再更新全量 SQL，并明确已纳入的增量范围。`CREATE TABLE IF NOT EXISTS` 不会更新已有表，不能用重跑全量初始化代替增量升级；不得为升级而自动清空或重建已有库。

当前全量结构按 MySQL 8.0.16+ 验证。既有开发环境的 MySQL 5.7 无法执行全部 CHECK 保障；数据库版本与运行时 SQL 的平台要求见 [SQL 规范](SQL脚本规范.md)。

## 已有库增量升级

后续增量脚本统一放在 `sql/migrations/`，按 `YYYY-MM-DD_NN_description.sql` 命名。已清理的历史脚本无需恢复，后续增量必须随对应结构变更交付。

1. 核对目标数据库、MySQL 版本、实际表结构和已执行记录，选择尚未执行且满足前置条件的增量；不能对未知结构盲目执行全部脚本。
2. 按脚本依赖与文件名顺序执行，先完成依赖的结构和必要数据变更，再启动依赖新结构的应用。脚本必须说明数据影响、重跑策略和部分失败后的恢复方式。
3. 保留现有业务数据；涉及字段转换或约束收紧时，先检查并处理不满足新规则的数据。
4. 执行后核对字段、索引、约束和必要数据，确认与全量基线叠加适用增量后的当前结构定义一致，并验证受影响功能。记录实际执行的脚本、环境与结果。

新库按上面的固定顺序执行 `01 → 02 → 03 → 04`，再初始化种子；已有库依据实际结构选择适用增量。仓库提供脚本不代表已在目标库执行。`00` 已合入当前全量基线，`01` 仅部分字段已合入，`02` 尚未合入；`03` 将符合基线的库保留原样，并修正其已覆盖的旧库结构差异；`04` 补齐空注释并按当前业务语义纠正旧注释。

### 2026-10-28 空值约束与字段注释

增量：[2026-10-28_00_nullability_and_comments.sql](../sql/migrations/2026-10-28_00_nullability_and_comments.sql)。本次按用户要求同步修改全量初始化 SQL，新库已包含这项变更。去重后涉及 44 张表、154 个字段：26 张表的 `is_deleted` 收紧为 `TINYINT NOT NULL DEFAULT 0`，`goal.user_id`、`b_video.user_id` 收紧非空，补齐 128 处字段注释。公共分类与匿名日志的空用户语义保持原约定。

执行顺序：本脚本使用同日序号 `00`，需先于 `2026-10-28_02_unify_common_fields.sql` 执行；后者会将本次清单中的 `enabled` 改名。完成后续字段重命名后，不再重跑本脚本；若误执行，字段预检会在任何业务 ALTER 前停止。

已有库使用支持 `DELIMITER` 的 mysql 客户端运行，兼容 MySQL 5.7.44 与 8.0。先暂停相关应用写入及定时任务，备份并核对目标库，确认目标表和字段均已存在。需要目标表的 SELECT/ALTER、临时表及存储过程权限；禁止使用 `--force` 跳过错误。脚本内固定严格模式并恢复调用连接原模式。

```bash
mysql --default-character-set=utf8mb4 --host <host> --port <port> --user <user> -p <database> \
  < sql/migrations/2026-10-28_00_nullability_and_comments.sql
```

全部结构与数据预检通过后才开始 ALTER。26 个删除标记不得为 NULL 或非 0/1；两个归属字段不得为 NULL，包括已软删除行。异常会报告表和列并停止，不自动回填、删除记录或指定默认用户。修复时必须按实际业务核实数据，再从头运行。脚本保留其他字段属性、现有数据和索引；每表合并 ALTER，已符合目标定义的字段跳过，支持部分成功后重跑。DDL 隐式提交，不能用 ROLLBACK 撤销；失败后先核对已完成范围。

2026-10-28 隔离验证使用 MySQL **5.7.44、8.0.40**：升级后的全部 **72 张表、1023 个列定义**与对应新建结构一致（含 COMMENT、默认值、字符集、自增及 ON UPDATE），索引和 44 张受影响表的测试数据保持不变。通过全部 28 个可空目标的异常拦截（包括软删除记录的空归属）、非法删除值拦截、缺表/类型不符时零业务 ALTER、升级后拒绝 NULL、重复执行和部分升级后重跑，以及自定义排序规则、带引号/反斜杠的默认值、时间精度与更新时间属性保留检查。

验证边界：8.0 使用完整原始建表脚本；5.7 测试建库时仅将基线已有的命名 CHECK 改为 5.7 可解析的匿名 CHECK，**增量脚本未作改写**。因此验证证明本增量适用于 5.7 已有库，不表示全量初始化原文件可直接在 5.7 执行或 CHECK 在 5.7 生效。该次空值/注释增量验证未连接、执行或验收业务数据库，也未运行业务 API 联调及客户端构建。

## 隐私协议与账号注销

当前 `user` 结构包含 `policy_version`、`policy_accepted_at`、`erasure_requested_at`、`erasure_retry_at`。注册需两端同步携带当前协议版本与明确同意标记；自助注销先停用账号，再由后台物理清理。新库使用当前全量结构；已有库必须通过增量补齐相关字段和索引后再启动对应功能。增量脚本为 [2026-10-27_01_user_privacy_erasure.sql](../sql/migrations/2026-10-27_01_user_privacy_erasure.sql)，补齐上述四个字段和 `idx_user_erasure_retry(is_deleted, erasure_retry_at)` 索引；既有字段及数据保持不变，同名定义冲突时报错。历史协议记录和普通停用账号保持 NULL，不自动同意协议或触发注销。

初始化数据 `sql/2_ini_data/2026-10-27_privacy_contact.sql` 只补缺 `privacy.operator` 与 `privacy.contact-email` 两项公开联系信息，不写入虚构值。管理员在“系统配置”填写真实运营主体和可收信邮箱后，两端匿名协议入口同步展示。实现及发布检查见[隐私政策与账号注销](隐私政策与账号注销.md)。

已有库执行顺序（在后端仓库目录执行，替换连接参数和库名）：

```bash
mysql --default-character-set=utf8mb4 --host <host> --port <port> --user <user> -p <database> \
  < sql/migrations/2026-10-27_01_user_privacy_erasure.sql
mysql --default-character-set=utf8mb4 --host <host> --port <port> --user <user> -p <database> \
  < sql/2_ini_data/2026-10-27_privacy_contact.sql
```

第一步成功后再执行第二步；两步均成功后启动新版应用。迁移账号需要 `ALTER`、`CREATE ROUTINE`、`ALTER ROUTINE`、`EXECUTE` 权限；第二步需要配置表查询与插入权限。脚本支持重复执行及部分字段已存在的情况，执行失败先按文件头说明核查，不能使用 `--force` 跳过错误。实际目标库执行情况须单独记录。

迁移保留已有 `user` 表的字符集和排序规则，`policy_version` 继承表默认值；不要求已有表为 `utf8mb4_unicode_ci`。旧版脚本的 `user table prerequisites do not match` 将缺表、引擎、缺列与排序规则差异混在同一错误中，不能仅凭该消息认定表结构错误。新版取消排序规则限制，并分别报告缺表、非 InnoDB、缺少 `nickname` 或 `is_deleted`。该前置检查发生在业务表 ALTER 之前；更新脚本后从头重跑即可重新校验并补齐缺项。

2026-10-27 本次增量在隔离 MySQL 5.7.44、8.0.40 验证通过：已有表升级、四个字段的 16 种部分存在组合、当前全量用户表重跑、列与索引定义对齐、数据保留、普通停用账号不进入注销查询、同名定义冲突及缺表报错、失败后修正重跑，以及隐私配置重复执行保留管理员值和软删除状态。验证只涉及隔离库的用户表和配置表，不代表目标业务库已升级或注销业务已完成真实联调。

同日修复排序规则前置检查后，在上述两个 MySQL 版本补测 `utf8mb4_general_ci`、`utf8mb4_unicode_ci`、`utf8_general_ci`，并在 8.0.40 补测 `utf8mb4_0900_ai_ci`：复现旧脚本误拒绝，修正版升级和重跑通过，原表排序规则与数据保持不变。另验证已有 `policy_version` 使用 `utf8mb4_bin` 时保留其定义，以及缺表、缺列、非 InnoDB、字段和索引冲突的明确报错及失败后恢复。尚未读取或修改报错的目标业务库。

```bash

```

## 既有库结构对齐

增量：[2026-10-28_03_schema_alignment.sql](../sql/migrations/2026-10-28_03_schema_alignment.sql)。在同日适用的 `00`、`01`、`02` 后执行；新库执行时已符合的定义会跳过，不修改全量初始化基线。

```bash
mysql --default-character-set=utf8mb4 --host <host> --port <port> --user <user> -p <database> \
  < sql/migrations/2026-10-28_03_schema_alignment.sql
```

覆盖范围：

- `expense.exp_type_id`、`income.inc_type_id` 对齐为有符号 `bigint`。转换前检查全部值为无空白的十进制整数、允许负号和前导零，且不超出类型范围；非法值报错停止，不截断或替换。
- `expense.user_id`、`income.amt` 收紧非空。包括软删除记录在内的 NULL 必须先按业务事实修复；脚本不猜测用户归属、不回填金额、不删除业务记录。

- `user_dict_type.id` 去除自增，保留现有 ID；`dict_name`、`dict_type` 的默认值改为 NULL，保留已有字段值。
- 删除当前应用不再使用的 `login_log.password`、`mail_log.content`。DROP COLUMN 会永久删除其中的历史内容，脚本不读取、输出或复制这些内容；执行前必须核对正在运行的版本不再读写这两列，并确认保留策略和清理范围。

兼容 MySQL 5.7.44 / 8.0；六张目标表须已存在且为 InnoDB。停止相关应用写入、任务和并发迁移，备份需要保留的业务数据。需 SELECT、ALTER、CREATE ROUTINE、ALTER ROUTINE、EXECUTE、CREATE TEMPORARY TABLES，以及读取相关表、索引、外键、CHECK、视图、存储过程和触发器定义的权限。全部结构、数据及依赖预检通过后才执行 ALTER；未知定义或同名索引冲突停止，已符合目标的项目跳过，支持部分完成后重跑。DDL 及删除内容不能由 ROLLBACK 恢复，失败后保持停写并核查已完成范围。

本增量不调整文章两表、系统字典唯一约束、额外普通索引、其他旧字典字段、已取消业务表、历史备份表或整表字符集。上述项目需先确认业务含义及保留用途；不能用重建表或批量删除差异的方式代替核实。迁移脚本的交付和隔离验证不代表目标业务库已执行结构升级。

`verify` 要求隔离 MySQL 8.0.16+，在不支持版本上拒绝执行；仅创建、删除随机命名的临时库，不写业务库。它按“全量基线 → `01_asset_purchase_source` → `02_unify_common_fields` → `03_schema_alignment` → `04_schema_comments` → 菜单和其他种子”初始化，检查首页路由、管理员菜单、手机号与微信唯一性、逻辑删除后重用、可空卡号和头像文件外键。MySQL 错误必须匹配预期约束错误，连接或语法错误不能当作通过。新增未合并增量时仍须维护此显式执行顺序。

## 只读结构预检

```bash
python3 scripts/check-database-schema.py --host <host> --port <port> --user <user> \
  preflight --database aio_life --expected <schema-contract.json>
```

`preflight` 支持 MySQL 5.7 与 8.0，只查询表、列、索引、CHECK、外键及表/字段 COMMENT，不执行迁移或修正数据。比较会归一化整数显示宽度、时间默认值语法、MySQL 8 的 `DEFAULT_GENERATED` 标记及 InnoDB 外键 `NO ACTION/RESTRICT` 等等价表示，仍保留类型、可空性、实际默认值、排序规则和注释差异。

MySQL 5.7 缺少可执行的 CHECK 保障：预检会继续完成其他结构比较，同时明确报告平台无法满足契约中的 CHECK，返回非零结果，不把“无法查询”或“数据库忽略 CHECK”判作通过。预检不比较业务数据，也不代表应用校验已替代这些约束；目标库升级、数据核验和部署须分别执行与记录。
