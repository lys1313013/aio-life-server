# 数据库初始化与验证

数据库同时维护当前全量结构、初始化数据和已有库升级所需的增量脚本。此前清理历史 SQL 仅针对已整理的旧脚本，后续结构变更仍须提供增量。后端、Web、Mobile 和 Query 使用当前契约一起更新；应用不保留旧接口兼容分支。

## 初始化

1. 在空库执行 `sql/1_init_table/2026-08-18_init_all_tables.sql`。
2. 执行 `sql/menu/2_ini_data/2_menu.sql` 建立基础菜单。
3. 按文件名顺序执行 `sql/2_ini_data/*.sql`，再执行 `sql/menu/2_ini_data/202*.sql`。

全量结构描述当前最终状态，用于空库初始化。修改表时同步全量 SQL、增量脚本、实体、Mapper、请求/响应与两端调用。`CREATE TABLE IF NOT EXISTS` 不会更新已有表，不能用重跑全量初始化代替增量升级；不得为升级而自动清空或重建已有库。

当前全量结构按 MySQL 8.0.16+ 验证。既有开发环境的 MySQL 5.7 无法执行全部 CHECK 保障；数据库版本与运行时 SQL 的平台要求见 [SQL 规范](SQL脚本规范.md)。

## 已有库增量升级

后续增量脚本统一放在 `sql/migrations/`，按 `YYYY-MM-DD_NN_description.sql` 命名。已清理的历史脚本无需恢复，后续增量必须随对应结构变更交付。

1. 核对目标数据库、MySQL 版本、实际表结构和已执行记录，选择尚未执行且满足前置条件的增量；不能对未知结构盲目执行全部脚本。
2. 按脚本依赖与文件名顺序执行，先完成依赖的结构和必要数据变更，再启动依赖新结构的应用。脚本必须说明数据影响、重跑策略和部分失败后的恢复方式。
3. 保留现有业务数据；涉及字段转换或约束收紧时，先检查并处理不满足新规则的数据。
4. 执行后核对字段、索引、约束和必要数据，确认与当前全量定义一致，并验证受影响功能。记录实际执行的脚本、环境与结果。

新库直接使用当前全量结构，不重复执行已经包含在全量中的增量。仓库提供脚本不代表已在目标库执行；现有初始化验证器不会自动运行增量脚本，须单独验证增量升级路径。

## 隐私协议与账号注销

当前 `user` 结构包含 `policy_version`、`policy_accepted_at`、`erasure_requested_at`、`erasure_retry_at`。注册需两端同步携带当前协议版本与明确同意标记；自助注销先停用账号，再由后台物理清理。新库使用当前全量结构；已有库必须通过增量补齐相关字段和索引后再启动对应功能。增量脚本为 [2026-10-27_01_user_privacy_erasure.sql](../sql/migrations/2026-10-27_01_user_privacy_erasure.sql)，补齐上述四个字段和 `idx_user_erasure_retry(is_deleted, erasure_retry_at)` 索引；既有字段及数据保持不变，同名定义冲突时报错。历史协议记录和普通停用账号保持 NULL，不自动同意协议或触发注销。

初始化数据 `sql/2_ini_data/2026-10-27_privacy_contact.sql` 只补缺 `privacy.operator` 与 `privacy.contact-email` 两项公开联系信息，不写入虚构值。管理员在“系统配置”填写真实运营主体和可收信邮箱后，两端匿名协议入口同步展示。实现及发布检查见[隐私政策与账号注销](隐私政策与账号注销.md)。

已有库执行顺序（在后端仓库目录执行，替换连接参数和库名）：

```bash
mysql --default-character-set=utf8mb4 --host <host> --port <port> --user <user> -p <database> \
  < sql/migrations/2026-10-27_01_user_privacy_erasure.sql
mysql --default-character-set=utf8mb4 --host <host> --port <port> --user <user> -p <database> \
  < sql/2_ini_data/2026-10-27_privacy_contact.sql
```

第一步成功后再执行第二步；两步均成功后启动新版应用。迁移账号需要 `ALTER`、`CREATE ROUTINE`、`ALTER ROUTINE`、`EXECUTE` 权限；第二步需要配置表查询与插入权限。脚本支持重复执行及部分字段已存在的情况，执行失败先按文件头说明核查，不能使用 `--force` 跳过错误。实际目标库执行情况须单独记录。

迁移保留已有 `user` 表的字符集和排序规则，`policy_version` 继承表默认值；不要求已有表为 `utf8mb4_unicode_ci`。旧版脚本的 `user table prerequisites do not match` 将缺表、引擎、缺列与排序规则差异混在同一错误中，不能仅凭该消息认定表结构错误。新版取消排序规则限制，并分别报告缺表、非 InnoDB、缺少 `nickname` 或 `is_deleted`。该前置检查发生在业务表 ALTER 之前；更新脚本后从头重跑即可重新校验并补齐缺项。

2026-10-27 本次增量在隔离 MySQL 5.7.44、8.0.40 验证通过：已有表升级、四个字段的 16 种部分存在组合、当前全量用户表重跑、列与索引定义对齐、数据保留、普通停用账号不进入注销查询、同名定义冲突及缺表报错、失败后修正重跑，以及隐私配置重复执行保留管理员值和软删除状态。验证只涉及隔离库的用户表和配置表，不代表目标业务库已升级或注销业务已完成真实联调。

同日修复排序规则前置检查后，在上述两个 MySQL 版本补测 `utf8mb4_general_ci`、`utf8mb4_unicode_ci`、`utf8_general_ci`，并在 8.0.40 补测 `utf8mb4_0900_ai_ci`：复现旧脚本误拒绝，修正版升级和重跑通过，原表排序规则与数据保持不变。另验证已有 `policy_version` 使用 `utf8mb4_bin` 时保留其定义，以及缺表、缺列、非 InnoDB、字段和索引冲突的明确报错及失败后恢复。尚未读取或修改报错的目标业务库。

## 自动验证

```bash
python3 scripts/test-database-schema.py
# 仅对隔离测试 MySQL 执行，连接凭据由 MYSQL_PWD 注入。
python3 scripts/check-database-schema.py --port 3306 verify
```

验证器仅创建、删除随机命名的临时库，不写业务库。它从当前全量结构和全部种子数据初始化，检查首页路由、管理员菜单、手机号与微信唯一性、逻辑删除后重用、可空卡号和头像文件外键。MySQL 错误必须匹配预期约束错误，连接或语法错误不能当作通过。

CI 的 `database-schema` 使用同一入口；保留 `schema-contract.json` 和 `schema-report.json`，供当前版本结构检查。脚本存在不代表本次已实际验证；以执行日志或 CI 结果为准。

## 只读结构预检

```bash
python3 scripts/check-database-schema.py --host <host> --port <port> --user <user> \
  preflight --database aio_life --expected <schema-contract.json>
```

预检只查询表、列、索引、CHECK 和外键。比较的是当前版本结构，不承担旧库升级或数据修正；不比较数据和 COMMENT。增量升级、部署及数据库重建需要单独执行与核实。

## 初始化数据约定

- 首页菜单使用 `/`，不生成 `/analytics`。
- 菜单 `status`、`mobile_status` 分别控制 Web 与 Mobile，操作日志仅在 Web 提供入口。
- 会员平台预设集中于 `2026-10-20_membership_providers.sql`；初始化只补缺失平台，保留管理员修改、停用和逻辑删除状态。
- LLM 会话、消息和模型密钥业务已取消，不初始化对应三张表。
- 文件表 `file_name` 保存完整对象键；普通附件以文件 ID 访问，CBTI 图片使用独立公共入口。
