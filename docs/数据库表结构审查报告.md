# AIO Life 数据库表结构审查报告

> 审查对象：`docs/数据库表结构.md`（由 `sql/1_init_table/2026-08-18_init_all_tables.sql` 及历史脚本合并生成）
> 审查日期：2026-08-18
> 审查方法：通读全部 41+ 张表定义，抽样核对 SQL 源文件（`expense` / `b_video` / `login_log` / `device`），文档与 SQL 一致。

## 结论摘要

| 严重级别 | 数量 | 说明 |
|---|---|---|
| P0（安全 / 数据完整性） | 5 | 明文存密码、日期类型错误、逻辑删除与唯一索引冲突 |
| P1（性能 / 关联正确性） | 7 | 关键表无索引、外键类型不匹配、双表重复 |
| P2（一致性 / 维护成本） | 6 | JSON 类型不统一、审计字段风格混乱、冗余字段无约束 |

多数问题源于演进期增量建表，属于技术债务而非致命错误，但其中 **login_log 明文存密码** 和 **device 日期用 varchar** 两项必须优先整改。

---

## P0 —— 安全与数据完整性

### 1. `login_log.password` 明文存密码 【高危】

- **位置**：`login_log.password` varchar(255)，注释"密码 密码错误时存储"
- **问题**：把用户输入的密码明文写进日志表。无论密码对错，明文密码进持久化存储都是泄露风险：日志泄露 = 账号密码泄露。
- **建议**：
  - 删除该字段；如需排查登录问题，只保留 `username` + `ip_address`。
  - 若确需记录失败凭据，只存单向哈希（与 `user.password` 的盐值哈希方案一致），且哈希和日志条目都无法被反查时才有意义，实际价值很低，默认删除。
- **同表附带**：`ip_address` 注释错写为"创建时间"，应修正；`user_id` 无索引，按用户查登录日志会全表扫（涉及 P1）。

### 2. `user_bind.access_token` 第三方令牌明文存储

- **位置**：`user_bind.access_token` text
- **问题**：GitHub / LeetCode / 扇贝等绑定账号的访问令牌明文落库。令牌等价于账号凭证，DB 一旦泄露即可冒用第三方身份。
- **建议**：改用可逆加密存储（复用 `password_vault` 的 SM4 方案），或只存带作用域/短期的 refresh token，访问令牌仅在内存中。

### 3. `device` 日期字段用 varchar(255) 【类型错误】

- **位置**：`device.purchase_date`、`device.end_date` varchar(255)
- **问题**：字段语义是日期，类型却是字符串。结果：
  - 无法做日期运算（`end_date - purchase_date` 计算日均费用直接失效）
  - 无法按日期范围查询 / 排序
  - 没有 DB 层格式校验，脏数据可随意写入
- **建议**：改 `date`。

### 4. 逻辑删除 + 唯一索引冲突（整库通病）

- **位置**：
  - `user.username`（uk_username）
  - `user_quick_nav`（uk_user_menu: user_id, menu_id）
  - `sys_dict_type.dict_type`（uk 同名索引）
  - `system_config.config_key`（uk_config_key）
  - `api_key.api_key`（uk_api_key）
  - `notification_channel_config`（uk_user_channel: user_id, channel）
  - `notification_preference`（uk_user_biz_channel）
  - `notification_delivery`（uk_dedup_user_channel）
- **问题**：字段带逻辑删除（`is_deleted`），同时存在唯一索引。软删后该记录仍占用唯一值，导致同用户名 / 同配置键 / 同 user+menu / 同 user+channel 无法再次插入。对 `user_quick_nav`、`notification_preference` 这类"一删一建"高频场景影响最直接。
- **建议**：统一采取以下任一策略，按表决策：
  - 唯一索引列追加 `is_deleted`：`UNIQUE KEY uk_user_menu (user_id, menu_id, is_deleted)`——删除后置 `is_deleted=1` 即可复用；逻辑上同一条记录只允许存在一份未删除数据。
  - 无法加列的（如 `api_key` 随机长串、`username`）：改用软删前校验"有效记录重名则拒绝"，或删除时对原值加后缀。
  - 约定写入技术文档：凡建"唯一约束 + 逻辑删除"的表，必须附带可复用的软删策略。

### 5. JSON 字段类型不统一（数据完整性风险）

- **位置**：`varchar` 存 JSON 的字段 —— `goal.tags`(1000)、`honor_record.tags`(500)、`milestone.tags`、`thought` 相关、`cbti_result` 部分字段；真 `JSON` 类型 —— `sys_menu.meta`、`b_video.pages_info`、`cbti_personality.vector/strengths/weaknesses`
- **问题**：同为 JSON 语义，实现方式两套。`varchar` 版本无结构校验，写入非法 JSON 应用层不察觉，读取时解析必炸。
- **建议**：统一为 MySQL 8 `JSON` 类型；存量 `varchar` 字段用 `ALTER TABLE ... MODIFY ... JSON` 迁移（先清理脏数据）。

## P1 —— 性能与关联正确性

### 6. `expense` / `income` 无任何业务索引 【性能硬伤】

- **位置**：`expense`、`income` 仅有 PRIMARY KEY
- **问题**：财务模块主查询是"按用户 + 时间区间汇总"，$2$ 张表都没有 `(user_id, exp_time / inc_date)` 索引，数据量上来后必然全表扫描。另：`expense.user_id` 是 `DEFAULT NULL` 且无 NOT NULL，与"账单必有归属"的业务矛盾。
- **建议**：
  ```sql
  ALTER TABLE expense ADD KEY idx_user_time (user_id, exp_time);
  ALTER TABLE income  ADD KEY idx_user_date (user_id, inc_date);
  ALTER TABLE expense MODIFY user_id bigint(20) NOT NULL COMMENT '用户ID';
  ```

### 7. `b_video` 索引配反：缺 `user_id` 索引

- **位置**：`b_video` 现有 6 个索引：status / progress / added_at / bvid / aid / title(100)
- **问题**：B 站记录按用户维度隔离（带 `user_id`），按用户查记录是最高频查询，但**没有 `user_id` 索引**；反而 `progress` 单列索引几乎无用（无按进度过滤的场景）。
- **建议**：
  ```sql
  ALTER TABLE b_video DROP KEY idx_progress;
  ALTER TABLE b_video ADD KEY idx_user_status (user_id, status);
  ALTER TABLE b_video ADD KEY idx_user_added (user_id, added_at);
  ```

### 8. 外键类型不匹配 【join 索引失效】

- **位置**：
  - `task.column_id` int(11) vs `task_column.id` bigint(20)
  - `expense.exp_type_id` int(11) / `income.inc_type_id` int(11) vs `user_dict_data.id` bigint(20)
  - `time_record` 内部：`id` varchar(32) / `category_id` varchar(32)，但 `relate_id` 指向的是 bigint 主键的业务表，`create_user` 又指 `user` 表的 bigint —— 同表关联类型不统一
- **问题**：类型不一致时 MySQL 无法用被驱动表索引做 join，或触发隐式转换导致索引失效；跨库将来做外键/迁移也会失败。
- **建议**：以目标表主键类型为基准对齐。`task_column.id`、`user_dict_data.id` 已是 bigint，把 `task.column_id`、`exp_type_id`、`inc_type_id` 统一为 `bigint(20)`；`time_record` 明确主键策略后（见 P2-10）统一关联列。

### 9. `task_detail` / `time_record` / `login_log` 关键查询无索引

- **位置**：
  - `task_detail` 无 `task_id` 索引 —— 按任务拉取明细必然全表扫
  - `time_record` 只有 `date` 单列索引，无 `(user_id, date)` 复合索引 —— 时迹按人按时段查是核心场景
  - `login_log` 无 `user_id` 索引
  - `device` 无 `user_id` 索引
- **建议**：
  ```sql
  ALTER TABLE task_detail ADD KEY idx_task_id (task_id);
  ALTER TABLE time_record ADD KEY idx_user_id_date (user_id, date);
  ALTER TABLE login_log ADD KEY idx_user_id (user_id);
  ALTER TABLE device ADD KEY idx_user_id (user_id);
  ```
- **additionally**：`time_record` 的 `create_user` 与 `user_id` 重复列（均注释"用户ID"），建议删除 `create_user`，保留 `user_id`。

### 10. `performance` / `performance_record` 双表重复

- **位置**：两张表字段几乎一致（演出名/类型/日期/城市/场馆/票价/座位/时长/评分/评价/购票平台/订单号）
- **问题**：疑似迁移残留。`performance` 缺 `user_id`（演出记录无归属用户，多用户系统不成立）；`performance_record` 缺 `user_id`、`is_deleted`（无软删）。职责边界不清。
- **建议**：确认业务语义后二选一：
  - A. 合并为一张 `performance`，补 `user_id` + 统一审计字段；`performancer_record` 迁移后删除。
  - B. 明确拆分：`performance` 为共享演出排期（无归属），`performance_record` 为个人观看记录（补 `user_id`）。
  - 无论哪种，先补 `user_id` + `(user_id, performance_date)` 索引。

### 11. `exercise_record` 字典关联类型偏离

- **位置**：`exercise_record.exercise_type_id` varchar(50)
- **问题**：运动类型是字典体系的"值"，其他字典消费方都用 bigint 主键关联（`user_dict_data.id`），此处却存 varchar 分类标识，查询/关联走不到字典表索引，且难做类型统一字典维护。
- **建议**：若运动类型引用 `user_dict_data`，改为 bigint 外键；若只是自由分类标识，保持 varchar 但加 `(user_id, exercise_date)` 索引并文档注明。

## P2 —— 一致性与维护成本

### 12. ID 策略三套并存

- **位置**：AUTO_INCREMENT bigint（大量历史表）、雪花 bigint（`password_vault`、`feedback` 等新表）、varchar(32) UUID（`time_record`、`file`）
- **问题**：跨表关联类型对不上是 P1-8 的根本原因；且 `file.id` 是 varchar(32) UUID，而各表的 `file_id` 列长度不一（varchar(32)/varchar(50)），恰恰该统一。
- **建议**：定一个唯一 ID 策略写进 AGENTS.md 约定，存量表渐进对齐。至少保证**关联列类型与主键类型严格一致**。

### 13. 审计字段风格混乱

- **位置**：`user` 用 `created_at/updated_at`；`sys_dict_type`/`sys_dict_data` 用 `create_by/update_by`（varchar 字符串）；其余用 `create_user/update_user`（bigint）。且 `create_user` 有的 NOT NULL 有的可空，无统一规则。
- **问题**：generated code / 公共基类难以统一处理，新人按表抄容易抄错。
- **建议**：统一为 `create_user/update_user` (bigint, 可空) + `create_time/update_time`（datetime），`user` 表的 `created_at/updated_at` 与字典表的 `create_by/update_by` 迁移对齐；`create_user` 统一默认可空（系统任务/初始化数据无创建人）。

### 14. 数据语义冗余无约束

- **位置**：
  - `goal`：`year/month/day` 与 `start_date/end_date` 重复；`progress` 与 `current_value/target_value` 重复
  - `b_video`：`progress` 与 `watched_duration/duration` 重复，`duration`=0 时进度计算除零
  - `read_record`/`movie`：`total_progress` 注释"总页数或 100 表示百分比"语义双关 + `current_progress`
  - `expense`：`amt` 与 `transaction_amt` 语义未定义（花费金额 vs 交易金额）
- **问题**：无 CHECK 约束，写库不校验，多列很快不一致，统计口径打架。
- **建议**：要么删冗余列只留来源列（`goal` 只留 `start_date/end_date`，删 `year/month/day`；进度只留 `progress`），要么加 `CHECK` 约束并在文档明确计算口径（`progress = current/target`；`b_video` 用 `watched_duration/duration`，DB 层 `CHECK duration > 0`）。

### 15. 枚举/状态字段类型与命名不一

- **位置**：
  - `honor_record.level` varchar(20) 存"1-校级 2-市级 3-省级 4-国家级 5-国际级"——数值语义存字符串
  - `task_detail.priority` 数值含义扭曲：1-高、10-中、20-低（数值大小与优先级语义相反）
  - `task_detail.is_starred` int(1) 却是布尔语义
  - `exercise_record.exercise_count` 无注释
- **建议**：纯枚举语义用 `tinyint` + 注释，或真 `ENUM`；`priority` 改为 1/2/3 单调递增语义；布尔统一 `tinyint(1)`。

### 16. 其余杂项

- `performance`、`performance_record`、`device` 等其他表缺少 `create_user/update_user` 或 `is_deleted`，与"多数业务表包含"约定不一致。
- `api_key_log` 无 `create_time` 索引（日志类表按时间查询是常态）。
- `notification_delivery.payload_ciphertext` mediumtext 存于库内，量大后可迁对象存储，仅留引用。
- `file.hash_value` 有索引但无唯一约束，防重依赖应用层，可接受但需在代码层保证。

## 建议整改顺序

**第一批（P0，直接改 schema）**
1. 删除 `login_log.password`
2. `device` 日期字段改 `date`
3. 统一逻辑删除 + 唯一索引策略，落库修正 6 处

**第二批（P1，索引/类型）**
4. `expense`/`income` 补 `(user_id, 时间)` 索引 + `user_id NOT NULL`
5. `b_video` 补 `user_id` 索引、删 `progress` 索引
6. 对齐 4 处外键类型（`task.column_id`、`exp_type_id`、`inc_type_id`、`time_record` 关联列）
7. `task_detail`/`time_record`/`login_log`/`device` 补索引
8. 合并或明确定位 `performance` / `performance_record`

**第三批（P2，一致性债务）**
9. 统一 JSON 类型
10. 统一审计字段命名
11. 清理冗余列 / 加 CHECK 约束
12. 统一枚举与布尔类型

> 注意：所有 `ALTER` 指令先评审数据迁移（尤其类型变更与唯一索引重建），避免线上数据截断或插入失败。
