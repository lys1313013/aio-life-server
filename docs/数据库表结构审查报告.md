## 待整改清单

### P1 —— 性能 / 关联正确性

| 问题 | 位置 | 整改 |
|---|---|---|
| `time_record` 索引形状错误 | `idx_time_record_date (date)` 单列索引 | 全系统最热表，但所有查询均为 `(user_id, date)` 联合条件（`TimeRecordController`、`RecordMcpTools`、`ITimeRecordMapper.xml` 统计 SQL）。单列 `date` 选择性极差，改为 `(user_id, date)` |
| `expense` / `income` 缺 `(user_id, 时间)` 索引 | `expense.exp_time`、`income.inc_date` | 两表仅主键。已确认列表查询均按 `(user_id, 时间范围)` 过滤并按时间倒序分页（`ExpController.query` / `IncomeController.query`），补复合索引 |
| `user_bind` 零二级索引 | 仅 PRIMARY KEY | 第三方同步/卡片渲染每次都按 `(user_id, platform)` 查（`UserBindServiceImpl.getBindByUserIdAndPlatform`，被 LeetCode/GitHub/Shanbay 三处高频调用），补联合索引 |
| `b_video` 缺 `user_id` 索引 | `b_video` | 列表按 `user_id + status` 过滤分页（`BVideoController.query`），补 `(user_id, status)` 或至少 `user_id` |

### P2 —— 一致性 / 维护成本

| 问题 | 位置 | 整改 |
|---|---|---|
| `performance` 没有 `user_id` 列 | 全库唯一例外 | 归属靠 `create_user` 判断（`PerformanceController.java:49`）。其他业务表均用 `user_id` 表归属、审计字段仅作审计；后续做管理端/数据迁移会踩坑，补 `user_id` 并迁移数据 |
| `record_article` / `record_article_annotation` 疑似死表 | 两表无 `user_id`，`IRecordArticleMapper` 除自身外零引用 | 确认是未完成功能还是废弃设计：未完成则补 `user_id` 与功能入口；废弃则删表 + 删实体/Mapper |
| `api_key_log` 只写不读且无限增长 | 只有插入路径（`ApiKeyInterceptor` → `ApiKeyLogServiceImpl.log`），无任何查询/清理路径 | 先定保留策略（定期清理或归档）；报告原列的「缺 create_time 索引」在无查询路径前提下优先级降低，建查询功能时再补 |
| `login_log` 无限增长 | 只写不清理 | 同上，定保留策略 |
| 删唯一索引后的并发兜底缺口 | `user.username` 注册路径 | `uk_username` 已删，注册用 `selectCount` 校验（`UserServiceImpl.java:431-435`），并发下可产生重名用户，之后登录 `selectOne` 抛 `TooManyResultsException` 导致该用户无法登录。单用户自部署风险低；建议 username 补普通索引（登录查询需要），接受校验竞态或加分布式锁兜底 |
| 其余唯一索引删除后的兜底确认 | `notification_preference`（find-then-insert 有兜底但存在并发重复窗口）、`system_config.config_key`、`api_key.api_key` 未逐一验证 | 逐一确认业务层有「有效记录唯一」兜底 |
| `honor_record.level` varchar 存数值 | varchar(20) 存「1-校级~5-国际级」（`HonorRecordEntity.level` 为 String） | 纯枚举改 `tinyint` + 注释 |
| `read_record` / `movie.total_progress` 语义双关 | 注释「总页数或 100 表示百分比」 | 明确语义或拆列 |
| `expense.amt` / `transaction_amt` 注释含糊 | 记账金额 vs 支付金额仅靠实体注释区分 | 同步库注释 |
| `income.inc_date` 命名/粒度不一致 | 同域 `expense.exp_time` 为 datetime，`inc_date` 为 date 命名孤立 | 统一命名与粒度 |
| `exercise_record.exercise_count` 无注释 | — | 补注释 |
| `file.biz_id` 与部分业务主键类型不兼容 | `file.biz_id` 为 bigint，但 `time_record.id`、`file.id` 自身是 varchar(32) | 这两类业务无法通过 `idx_biz (biz_type, biz_id)` 反向关联；若未来需要，biz_id 改 varchar(64) 或接受限制并文档化 |
| `login_log.ip_address` 列注释错误 | 建表脚本中注释写成「创建时间」（复制粘贴错误） | 改脚本注释为「登录IP」，存量库可不同步 |
| `message.sender_id` NOT NULL 与系统通知冲突 | `type=0` 系统通知没有真实发送用户 | 放宽可空，或约定系统发送者伪 ID 并文档化 |
| `password_vault.username` 明文存储 | 注释「明文存储，便于展示」，与同表 password/remark 前端加密的设计不一致 | 账号本身也是敏感信息，评估是否同样走前端 SM4 加密；若维持明文需明确决策理由 |

### P3 —— 低优先级 / 观察项

| 问题 | 位置 | 说明 |
|---|---|---|
| `is_deleted` 类型混乱 | 约 10 张表用 `int(11)`，其余 `tinyint`/`tinyint(1)`/`tinyint(4)` 混用 | 不影响正确性（MyBatis Plus 全局配置），新表统一 tinyint 即可，存量不回改 |
| `goal.year/month/day` 与 `start_date/end_date` 双套时间维度 | 两套均可空，筛选口径易歧义；且 year/month/day 是 MySQL 关键字 | 观察项：查询逻辑稳定前不动；若改，以 start_date/end_date 为准派生年月日 |
| `thought.user_id` 为 `bigint(19)` | 与全库 `bigint(20)` 口径不一致 | 无害，新表注意口径即可，存量不回改 |
| 零散缺二级索引 | `thought_rela_event.thought_id`、`task_detail.task_id`、`memo.user_id`、`thought.user_id` | 单用户量级下无实际影响，量级上来再补 |

## 已决策不回改

- `login_log.password` 明文存密码 —— **有意保留**：登录失败时记录明文密码，用于抓取弱密码/常见密码样本构建密码本（既非缺陷也非疏漏，属刻意设计）。注释已写清于建表脚本 / `docs/数据库表结构.md` / `LoginLogEntity` / `UserServiceImpl.login()`，勿删勿改。
- `time_record.id` 保持 varchar(32)（前端 UUID 方案）、`relate_id` 保持 bigint 外链、`start_time/end_time` smallint 分钟表示 —— 既定设计，不在整改范围。
