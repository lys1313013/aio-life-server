### 5. JSON 字段类型不统一（数据完整性风险）

- **位置**：`varchar` 存 JSON 的字段 —— `goal.tags`(1000)、`honor_record.tags`(500)、`milestone.tags`、`thought` 相关、`cbti_result` 部分字段；真 `JSON` 类型 —— `sys_menu.meta`、`b_video.pages_info`、`cbti_personality.vector/strengths/weaknesses`
- **问题**：同为 JSON 语义，实现方式两套。`varchar` 版本无结构校验，写入非法 JSON 应用层不察觉，读取时解析必炸。
- **建议**：统一为 MySQL 8 `JSON` 类型；存量 `varchar` 字段用 `ALTER TABLE ... MODIFY ... JSON` 迁移（先清理脏数据）。

## P1 —— 性能与关联正确性

### 8. 外键类型不匹配 【join 索引失效】

- **位置**：
  - `task.column_id` int(11) vs `task_column.id` bigint(20)
  - `expense.exp_type_id` int(11) / `income.inc_type_id` int(11) vs `user_dict_data.id` bigint(20)
  - `time_record` 内部：`id` varchar(32) / `category_id` varchar(32)，但 `relate_id` 指向的是 bigint 主键的业务表，`create_user` 又指 `user` 表的 bigint —— 同表关联类型不统一
- **问题**：类型不一致时 MySQL 无法用被驱动表索引做 join，或触发隐式转换导致索引失效；跨库将来做外键/迁移也会失败。
- **建议**：以目标表主键类型为基准对齐。`task_column.id`、`user_dict_data.id` 已是 bigint，把 `task.column_id`、`exp_type_id`、`inc_type_id` 统一为 `bigint(20)`；`time_record` 明确主键策略后（见 P2-10）统一关联列。

### 11. `exercise_record` 字典关联类型偏离

- **位置**：`exercise_record.exercise_type_id` varchar(50)
- **问题**：运动类型是字典体系的"值"，其他字典消费方都用 bigint 主键关联（`user_dict_data.id`），此处却存 varchar 分类标识，查询/关联走不到字典表索引，且难做类型统一字典维护。
- **建议**：若运动类型引用 `user_dict_data`，改为 bigint 外键；若只是自由分类标识，保持 varchar 但加 `(user_id, exercise_date)` 索引并文档注明。

## P2 —— 一致性与维护成本

### 12. ID 策略三套并存

- **位置**：AUTO_INCREMENT bigint（大量历史表）、雪花 bigint（`password_vault`、`feedback` 等新表）、varchar(32) UUID（`time_record`、`file`）
- **问题**：跨表关联类型对不上是 P1-8 的根本原因；且 `file.id` 是 varchar(32) UUID，而各表的 `file_id` 列长度不一（varchar(32)/varchar(50)），恰恰该统一。
- **建议**：定一个唯一 ID 策略写进 AGENTS.md 约定，存量表渐进对齐。至少保证**关联列类型与主键类型严格一致**。

### 13. 审计字段风格混乱

- **位置**：`user` 用 `created_at/updated_at`；`sys_dict_type`/`sys_dict_data` 用 `create_by/update_by`（varchar 字符串）；其余用 `create_user/update_user`（bigint）。且 `create_user` 有的 NOT NULL 有的可空，无统一规则。
- **问题**：generated code / 公共基类难以统一处理，新人按表抄容易抄错。
- **建议**：统一为 `create_user/update_user` (bigint, 可空) + `create_time/update_time`（datetime），`user` 表的 `created_at/updated_at` 与字典表的 `create_by/update_by` 迁移对齐；`create_user` 统一默认可空（系统任务/初始化数据无创建人）。

### 14. 数据语义冗余无约束

- **位置**：
  - `goal`：`year/month/day` 与 `start_date/end_date` 重复；`progress` 与 `current_value/target_value` 重复
  - `b_video`：`progress` 与 `watched_duration/duration` 重复，`duration`=0 时进度计算除零
  - `read_record`/`movie`：`total_progress` 注释"总页数或 100 表示百分比"语义双关 + `current_progress`
  - `expense`：`amt` 与 `transaction_amt` 语义未定义（花费金额 vs 交易金额）
- **问题**：无 CHECK 约束，写库不校验，多列很快不一致，统计口径打架。
- **建议**：要么删冗余列只留来源列（`goal` 只留 `start_date/end_date`，删 `year/month/day`；进度只留 `progress`），要么加 `CHECK` 约束并在文档明确计算口径（`progress = current/target`；`b_video` 用 `watched_duration/duration`，DB 层 `CHECK duration > 0`）。

### 15. 枚举/状态字段类型与命名不一

- **位置**：
  - `honor_record.level` varchar(20) 存"1-校级 2-市级 3-省级 4-国家级 5-国际级"——数值语义存字符串
  - `task_detail.priority` 数值含义扭曲：1-高、10-中、20-低（数值大小与优先级语义相反）
  - `task_detail.is_starred` int(1) 却是布尔语义
  - `exercise_record.exercise_count` 无注释
- **建议**：纯枚举语义用 `tinyint` + 注释，或真 `ENUM`；`priority` 改为 1/2/3 单调递增语义；布尔统一 `tinyint(1)`。

### 16. 其余杂项

- `device` 缺少 `create_user`、`create_time`、`update_user`、`update_time` 和 `is_deleted`；`task`、`task_column`、`honor_category` 等表也存在部分审计字段缺失。若这些表属于统一审计及逻辑删除规范的适用范围，应补齐字段；日志表、枚举表等例外需在表结构约定中单独说明。

- `api_key_log` 无 `create_time` 索引（日志类表按时间查询是常态）。

- `notification_delivery.payload_ciphertext` mediumtext 存于库内，量大后可迁对象存储，仅留引用。

## 建议整改顺序

**第一批（P0，直接改 schema）**
1. 删除 `login_log.password`
2. `device` 日期字段改 `date`
3. 统一逻辑删除 + 唯一索引策略，落库修正 6 处

**第二批（P1，索引/类型）**
4. `expense`/`income` 补 `(user_id, 时间)` 索引 + `user_id NOT NULL`
5. `b_video` 补 `user_id` 索引、删 `progress` 索引
6. 对齐 4 处外键类型（`task.column_id`、`exp_type_id`、`inc_type_id`、`time_record` 关联列）
7. `task_detail`/`time_record`/`login_log`/`device` 补索引

**第三批（P2，一致性债务）**
9. 统一 JSON 类型
10. 统一审计字段命名
11. 清理冗余列 / 加 CHECK 约束
12. 统一枚举与布尔类型

> 注意：所有 `ALTER` 指令先评审数据迁移（尤其类型变更与唯一索引重建），避免线上数据截断或插入失败。

## 仍存在的 P2 —— 冗余 / 死字段 / 命名

1. **`b_video` 死字段**：`progress`、`last_watched`、`added_at` 实体未映射、代码零引用，`idx_progress` 为死索引；`progress` 与 `watched_duration/duration` 语义重复。建议删列 + 删索引。
2. **`goal` 冗余**：`year/month/day` 与 `start_date/end_date` 重复；`progress` 与 `current_value/target_value` 重复，且无 CHECK 约束。
3. **`task_detail.priority`**：1高 / 10中 / 20低 数值与语义倒置；`is_starred int(1)` 布尔语义。
4. **`honor_record.level`**：varchar(20) 存数值级别（1-校级~5-国际级）。
5. **`read_record` / `movie` 的 `total_progress`**：注释「总页数或 100 表示百分比」语义双关。
6. **`expense.amt` / `transaction_amt`**：语义仅靠实体注释区分（记账金额 / 支付金额），库注释含糊，应同步。
7. **`time_record.create_user`（:346）**：审计列注释误标「用户ID」，与真实归属列 `user_id`（:345）混淆，应注释「创建人」。
8. **`thought.content`（:551）**：注释错别字「没人」，应为「内容」。
9. **`income` 命名孤立**：主键 `income_id` → `id` ✅ 已修复（`2026-08-22_unify_income_primary_key.sql`）。仍遗留：日期列 `inc_date` 命名及其 `date` 粒度与同域 `expense.exp_time`（datetime）不一致。
10. **`enum_type`**：仍用 `created_at/updated_at` 且无 `is_deleted` —— 属例外表，但未在表结构约定中文档化，新人易抄错。
