# SQL 脚本规范

适用范围：本仓库新增或修改的全量建表、增量迁移与数据初始化脚本。结构变更必须提供可执行的增量脚本；日常新增不可改写的 Flyway `V` 迁移，由用户在选定时间节点生成完整 `B` 基线并保留旧增量；此前清理历史脚本不取消后续增量维护。执行流程见[数据库初始化与验证](数据库初始化与验证.md)，当前结构见[数据库表结构](数据库表结构.md)。


## 1. 支持范围

只支持 PostgreSQL 18+，使用真实 PostgreSQL 验证初始化、增量和业务 SQL。旧库结构、数据及历史修正 SQL 仅在 Git 历史追溯，不保留本地副本或旧执行入口；当前只维护 PostgreSQL SQL。新表及每个字段必须有准确的中文 COMMENT，索引与约束必须说明用途。凭据、实际部署地址和个人数据不得进入 SQL 或仓库。

## 2. 目录、命名与格式

| 内容 | 目录或入口 | 要求 |
| --- | --- | --- |
| 全量初始化基线 | `sql/migrations/B<版本>__description.sql` | 冻结快照；新库采用最新基线及其后的增量，不部分合并 |
| 结构及数据增量 | `sql/migrations/VYYYYMMDD_NN__description.sql` | 唯一版本、按版本顺序执行；菜单、字典及数据修正也使用 V 迁移 |
| 原始资料 | `sql/reference/` | 维护来源与许可，生成器输出待审阅文件，不覆写已执行迁移 |
| 执行与结构说明 | `tools/flyway/pom.xml`、`docs/数据库初始化与验证.md`、`docs/数据库表结构.md` | 迁移执行、真实结构比对和业务定义分别维护 |

- `V` 版本可增加序号层级，例如 `V20261111_01_001__menu_data.sql`。文件名分隔符为双下划线 `__`；版本唯一，不能补入低于已发布版本的新迁移。
- 历史归档按用途整理：同类可以合并，结构、注释、菜单、字典、配置、地区、日历及独立业务预设分开；保留原版本、来源和依赖顺序。日常不改写已执行的 PostgreSQL V 迁移；2026-11-10 聚合公共种子的分类拆分是本次明确要求的整理，已有库先执行[一次性拆分登记](数据库初始化与验证.md#已执行旧公共种子的库一次性拆分登记)，不作为未来直接改写历史的先例。
- 已在持久环境执行的迁移不得修改、删除或重排；修正新增版本。基线合并生成新的 `B` 文件，不覆盖旧基线或删除升级路径。已有库不会重新执行新基线。
- 数据库通过独立 Flyway 入口迁移，不在应用启动时运行；Flyway 历史表属于工具基础设施，业务表实体校验只排除明确的 `flyway_schema_history`，不能扩大豁免范围。
- SQL 执行文件统一放在 `sql/migrations/`，不另设历史兼容目录。当前独立 PostgreSQL 版本链从 V20261110_01 开始；不将旧库迁移历史登记为 PostgreSQL 基线。

- 使用 UTF-8；SQL 关键字与类型使用大写，表名、列名使用英文小写下划线必要时使用双引号引用，保留字 user 必须始终引用。
- 每个字段、索引、约束单独占行，缩进统一为两个空格，语句以分号结束。
- 数据库编码使用 UTF8；业务普通文本用 ICU `aio_unicode_ci`，外部精确标识符保留确定性排序。PG 18 支持非确定排序下的 LIKE；正则表达式操作显式使用确定性 `COLLATE "C"`。
- 索引使用 `idx_<table>_<purpose>`，唯一索引使用 `uk_<table>_<purpose>`，CHECK 使用 `ck_<table>_<rule>`；已有名称不为统一格式而无故重命名。
- 全部迁移由调用方显式指定目标库，不在脚本中写 `CREATE DATABASE`、`USE` 或跨库限定表名；凭据只从运行环境注入。

说明只维护当前规则和必要的执行条件；不再创建按日期堆叠的 SQL 操作说明、独立菜单执行入口或手工迁移清单。工具输出记录实际测试结果，不将旧验证流水复制到操作指南。冻结 B/V 中的原始格式和来源注释不为排版而改写；新 SQL 全部按本规范编写。

## 3. 文件头必须说明执行条件

每份新增脚本都包含以下信息。对建表或纯注释脚本，也要明确“不回填数据”或“仅修改元数据”。

```sql
-- 目的：初始化当前业务所需默认数据。
-- 前置：已执行全量初始化基线及尚未合并的适用增量；数据库版本符合本文件要求。
-- 影响：只补缺失数据，不覆盖管理员配置。
-- 重跑：可重复执行，不恢复软删除项。
-- 执行：通过 mvn -f tools/flyway/pom.xml compile flyway:migrate 执行，遇错停止。
```

## 4. 注释写什么

注释表达字段的业务含义，不重复字段类型，不使用“字段”“数据”“信息”等没有具体含义的文字。

| 字段类别 | 必须说明 | 示例 |
| --- | --- | --- |
| 主键 | 标识对象、生成方式 | `足迹ID，由应用生成雪花ID` |
| 用户归属/引用 | 所属对象或引用对象 | `所属用户ID，用于用户数据隔离` |
| 版本 | 初始值和递增规则 | `乐观锁版本号，从1开始，每次编辑递增` |
| 状态/布尔/枚举 | 全部有效值及含义 | `逻辑删除标记：0=未删除，1=已删除` |
| 日期/时间 | 业务时点、精度、特殊值；涉及时区时注明约定 | `结束日期，9999-12-31表示至今` |
| 金额/数量 | 单位、零值和 NULL 含义 | `余额，单位元；NULL表示未记录，0表示零余额` |
| 经纬度 | 经度或纬度、坐标系、单位 | `经度，GCJ02坐标，单位度` |
| 第三方标识 | 供应商、用途、为空的情况 | `百度地点UID，手动选点或未获取时为空` |
| 可空业务字段 | NULL 的业务含义 | `详细地址，可补充楼栋和房号，未填写时为空` |
| 审计字段 | 记录的是谁或什么时间 | `最后更新人用户ID，未记录时为空` |

通用主键、审计字段等简单字段使用简短注释即可。存在特殊规则时必须写清，不能为了简短省掉特殊值或单位。

```sql
-- 按用户和删除状态筛选，并按开始日期排序读取足迹。
CREATE INDEX idx_footprint_user_start ON life_footprint (user_id, is_deleted, start_date);
COMMENT ON INDEX idx_footprint_user_start IS '按用户、逻辑删除和开始日期检索';
-- 结束日期不得早于开始日期；9999-12-31 表示至今。
ALTER TABLE life_footprint ADD CONSTRAINT ck_footprint_end CHECK (end_date >= start_date);
```

## 5. 字段与约束设计

跨表同义字段、单位、状态取值及冗余保留理由集中维护在[数据库设计审查与字段规范](数据库设计审查与字段规范.md)。新增字段先核对该文档；其中目标命名不代表已有字段已完成迁移。

- ID 使用 BIGINT，与现有雪花 ID 和实体映射一致；API 按项目约定输出字符串。
- 精确到日使用 DATE，日期时间使用项目既有 TIMESTAMP WITHOUT TIME ZONE 约定；不为方便展示而保存日期字符串。
- 金额和需要固定精度的坐标使用 NUMERIC，明确精度及单位。金额字段与接口的序列化遵循对应业务契约。
- 必填字段明确 NOT NULL。不要为了迁移成功而盲目添加 0、空字符串或某个日期作为默认值。
- 特殊值必须在表注释/字段注释、实体、接口、展示和校验中保持一致。例如生活足迹只用 `end_date = '9999-12-31'` 表示至今，不再同时保存 `ongoing`，界面显示“至今”。
- CHECK、唯一索引和外键按实际业务设计，约束名可定位问题。业务不要求唯一的组合不能擅自添加唯一约束。
- CHECK 不能替代 NOT NULL；判断结果为 NULL 的表达式不能被当作必填校验。
- 索引依据实际过滤、关联、排序设计；说明复合索引顺序和唯一键对逻辑删除的处理，不能简单把 `is_deleted` 加入所有唯一索引。
- 沿用 `is_deleted` 和 BaseEntity 审计字段。没有真实需求时，不新增幂等键、冗余状态或其他控制字段。

## 6. 结构修改、增量升级与初始化

- 每次新增、修改或删除表、字段、索引和约束，都必须提供已有库可执行的增量脚本；日常新增不可改写的 Flyway `V` 迁移，由用户在选定时间节点生成完整 `B` 基线并保留旧增量；不能以尚未上线或曾清理历史脚本为由省略增量。
- 增量脚本在文件头声明目标 PostgreSQL 版本、适用的变更前结构、依赖顺序、数据影响、必要回填、重跑策略与验证方式。需要回填时按业务规则保留现有数据，不伪造默认值。
- Flyway 成功执行的版本不会自动重跑；脚本仍须说明部分失败恢复策略。声明可重跑的步骤须检查实际结构，不能吞掉任意 SQL 错误后视为成功。普通 PostgreSQL DDL 在事务中执行，失败应回滚并验证数据保留；CREATE INDEX CONCURRENTLY 等非事务语句必须单独声明并制定恢复步骤。不能把 `repair` 当作结构修复，也不能用它掩盖已执行文件被改写。
- 增量用于把已有库升级到当前结构；应用不因此保留旧字段双写、旧接口或旧客户端兼容分支。已清理的历史脚本不要求重新恢复，后续新增增量须保留以供尚未升级的环境执行。
- `CREATE TABLE IF NOT EXISTS` 不会更新已有表；全量初始化仅用于空库，不把重跑当作开发库升级。
- 结构修改同步实体、Mapper、当前请求/响应、两端调用与表结构文档。
- 初始化脚本说明重跑策略。补缺操作不得覆盖管理员配置、用户修改或软删除状态；这是当前初始化与日常维护语义。
- 不自动清空或重建既有开发库；本任务没有数据库操作授权时，只交付仓库中的增量脚本和相关文档，不执行数据库变更。

## 7. 同步与验收

提交前逐项检查：

1. 每张新增表和每个新增/修改字段均有非空、准确的 COMMENT，通用字段无例外。
2. 索引、约束的用途有说明，注释与 NULL、默认值、枚举和特殊值一致。
3. 全量初始化基线叠加尚未合并的增量所得结构、已有库增量执行后的结构、实体和结构文档一致；交付说明列出本次增量脚本与执行顺序。
4. 结构变更同步实体、Mapper、请求/响应和客户端；新增业务表按后端规范通过真实 PostgreSQL 全字段查询。
5. 根据变更范围分别验证空库初始化，以及从声明的变更前结构执行增量后的结果、既有数据保留、错误路径和声明支持的重跑行为。现有初始化 CI 不等于增量验证通过。不能拿 H2 结果代替 PostgreSQL 专属 DDL 验证。
6. 纯文档、SQL 行注释或数据库 COMMENT 调整，检查差异、引用、脚本语法及列属性保持；不默认运行全量业务测试或客户端构建。尚未执行实际 SQL 时明确说明。
7. 当前 v6 PostgreSQL 结构契约与 Flyway 执行入口配套，包含表和字段注释；结构对比通过表示与当前契约一致，仍需审查注释是否准确表达业务含义。实际执行结构后，可用 `pg_get_constraintdef`、`pg_get_indexdef` 与 `col_description` 核对。

本规范适用于后续新增和修改的 SQL。脚本纳入 Flyway 不代表目标库已迁移；不能以文档或工具接入代替实际执行与验收。

## 8. 生活足迹参考

## PostgreSQL 参数与事务

JSON 使用 jsonb，二进制使用 bytea，数字状态保持 smallint/integer；Boolean 实体通过 NumericBooleanTypeHandler 映射 0/1。分页使用 LIMIT/OFFSET。字符串参数在变参函数 CONCAT 中显式 CAST 为 text，不能依赖未知参数类型推断。

可忽略的唯一键冲突使用 Mapper 的 ON CONFLICT，不捕获重复键后继续同一事务。UPDATE 对同一列只能赋值一次，需要清空的可空字段显式 set null。DESC 排序按业务声明 NULLS LAST，不能依赖数据库的默认 NULL 顺序。数据库默认不自动执行 ON UPDATE，业务审计在实体/Mapper 中维护。

Druid 的 connect-timeout/socket-timeout 使用毫秒，只在连接池配置；不要把 PostgreSQL 驱动的秒数放入同名 URL 参数，Druid 1.2.24 会按毫秒重新应用。
