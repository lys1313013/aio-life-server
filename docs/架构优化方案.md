## P1 —— 稳定性 / 性能（近期）

### 1. 第三方 HTTP 调用统一治理

飞书客户端有 3s/5s 超时（`FeishuAppClient`），标准存在但未统一：

| 调用方 | 问题 | 位置 |
|---|---|---|
| LeetCode GraphQL | `new RestTemplate()` 无任何超时，可无限挂起 | `config/RestTemplateConfig.java:10-12` → `client/LeetcodeClient.java:81,111,208` |
| GitHub GraphQL / Events | Hutool `HttpUtil` 未设超时（默认 -1 无限） | `GithubServiceImpl.java:49-57`、`GithubCardProvider.java:166,183` |
| 扇贝 | 同上 | `ShanbayCardProvider.java` |
| CSDN | Jsoup 默认 30s 偏长 | `CsdnServiceImpl.java:32,82` |

整改：

1. `RestTemplateConfig` 统一配置 connect 3s / read 10s（`ClientHttpRequestFactory`）
2. Hutool 调用点显式 `.timeout(...)`
3. 抽一个 `HttpClients` 工具类收敛所有外部调用，超时/重试一处定义

### 2. 批处理单点容错

`LeetcodeServiceImpl.check():125-130` 定时任务串行遍历所有绑定用户，循环内无 try/catch，单用户失败中断整批；`notifyTodayQuestion():298-316` 同样。整改：per-user try/catch，失败记日志继续，必要时累计失败告警。

### 3. Dashboard 第三方卡片加缓存

`/card/GITHUB`、`/card/LEETCODE`、`/card/SHANBAY` 每次刷新都实时跨境调用 1-3 次（无超时、无结果缓存，只缓存了可见性）。整改：结果缓存 5-15 分钟（Caffeine 即可，key 含 userId），刷新按钮走缓存失效。LeetCode 现有本地缓存多实例不一致（`LeetcodeServiceImpl.java:103,114`），单实例无碍，上多实例前需处理。

### 4. 异步化

全项目无 `@Async`：SMTP 邮件同步阻塞发送（`MailServiceImpl.java:62,103`），注册/重置密码接口延迟受 SMTP 抖动影响。整改：`@EnableAsync` + 邮件发送异步化（注意异步方法内不能再依赖 RequestContext）。

### 5. 事务缺口

| 位置 | 问题 | 整改 |
|---|---|---|
| `HonorRecordController.java:65-75` | 先插荣誉记录再 `bindBizId`（两独立事务），绑定失败留无附件记录 | 纳入同一事务 |
| `TaskController.java:120-131` reSort | 循环单条 UPDATE 无事务，部分失败即半成品排序 | 改批量 + `@Transactional` |
| `BVideoController.java:187-222` syncProgress | selectOne→insert/update 竞态，可产生重复行 | 加 `(user_id, bvid)` 唯一约束或 upsert |

## P2 —— 结构 / 可维护性（中期）

### 1. record 上帝模块拆分

record 现有 27 个 ServiceImpl、35 个 Controller，承载时迹/任务/目标/财务/荣誉/备忘/消息/第三方同步/仪表盘/文件/CBTI 等十几个领域。按领域逐步拆出：

```
record（保留：时迹、任务、目标 —— 核心记录引擎）
├── finance      ← expense、income
├── media        ← movie、read_record、b_video、performance
├── notify       ← message、notification_*、mail
├── sync         ← LeetCode/CSDN/GitHub/Shanbay client + autotask
└── file         ← file 表、MinIO、SysFileController
```

不必一次到位：新功能先落新包，存量随改动逐步迁移。

### 2. BaseEntity 挪到 core

`BaseEntity` 在 `record.pojo.entity`，却被 feedback/membership/sso/system/wardrobe 5 个模块跨包依赖，公共基类位置倒置（core 里已有 `AuditEntity`）。整改：`BaseEntity` 移入 `core.pojo.entity`，全量替换 import（纯机械变更）。

### 3. Controller 直连 Mapper 收敛

`BVideoController`、`TaskController`、`GoalController`、`HonorRecordController`、`ExpController`、`IncomeController`、`DeviceController`、`PerformanceController` 等 11+ 个 Controller 绕过 Service；`TaskServiceImpl` 整个类只是 `super.updateBatchById` 转发，业务校验（归属、审计字段）散落在 Controller。整改：Controller 只留参数解析与组装，持久化一律走 Service；空壳 Service 要么补业务要么合并。

### 4. 审计字段自动填充

全项目无 `MetaObjectHandler`，靠手工 `fillCreateCommonField`，已发生遗漏：`BVideoController.insert:70-93` 漏设 `createUser/createTime/isDeleted`；`ReadRecordServiceImpl.saveRecord:83-85`、`MovieServiceImpl.java:87-89` 依赖 DDL 默认值兜底。整改：实现 MyBatis Plus `MetaObjectHandler` 统一填充 `create_user/create_time/update_user/update_time`，业务代码不再手工赋值。

### 5. SQL 迁移版本化

当前 `sql/1_init_table`、`2_ini_data` 全靠手工按序执行，无已执行记录、无回滚，多环境易漂移（`docs/数据库表结构.md` 已与 DDL 实际状态漂移：4 张表缺失 + 至少 4 处列级过期）。整改：

1. 引入 Flyway，存量脚本按日期归入 baseline
2. `docs/数据库表结构.md` 改为从 DDL 或 `information_schema` 自动生成（CI 或脚本触发），废止手工合并

## P3 —— 表结构遗留（随改动顺带）

以下为 `docs/数据库表结构审查报告.md` 未覆盖项：

| 问题 | 说明 | 建议 |
|---|---|---|
| `record_article` / `record_article_annotation` 死表 | 已确认只有 Entity + Mapper，零业务引用 | 删表 + 删实体/Mapper |
| 26 张表 DDL 标 `AUTO_INCREMENT` 但实体全部走雪花 | 自增从未发生，DDL 与真实行为不符 | DDL 去掉 AUTO_INCREMENT 或文档注明历史遗留 |
| `b_video.user_id` / `goal.user_id` 可空 | `expense.user_id` 已收紧 NOT NULL，口径不一 | 收紧为 NOT NULL |
| `file.biz_id` bigint vs `time_record.id` varchar(32) | 附件体系无法反向关联 varchar 主键业务 | 接受现状或 `biz_id` 改 varchar |
| 分类体系 5 套并存 | `sys_dict_data`、`user_dict_data`、`time_tracker_category`、`honor_category`、`wardrobe_category` | 长期收敛到 `user_dict_data`（已有 template_id/color/icon/ext_data） |
| `message` 与 `notification_*` 两套消息体系并存 | 功能重叠，边界不清 | 明确边界：message=站内信，notification_*=外发渠道投递 |
| `sys_dict_data` 同存 `dict_id` + `dict_type` | 冗余可漂移 | 保留 `dict_type` 查询便利，以 `dict_id` 为准并加一致性说明 |
