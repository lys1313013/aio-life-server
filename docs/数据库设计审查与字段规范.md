### D01：唯一性不能只靠先查再写

| 业务唯一键（只针对有效记录） | 当前证据与风险 |
| --- | --- |
| `user.username` | [UserServiceImpl](../src/main/java/top/aiolife/sso/service/impl/UserServiceImpl.java) 的 `register` 先 `selectCount` 后插入；不同邮箱同时注册同一用户名可同时通过。DDL 无用户名唯一键，`login` 用 `selectOne`，重复后可能阻断登录 |
| `user.email` | 同一服务按邮箱检查注册唯一性，找回密码又按邮箱 `selectOne`，但 DDL 无邮箱唯一键。验证码流程不是覆盖所有写入口的数据库唯一性约束；应与用户名一起补齐，并明确空值、大小写和归一化规则 |
| `user_bind(user_id, platform)` | [UserBindController](../src/main/java/top/aiolife/record/api/UserBindController.java) 的普通平台新增先查询后 `save`；[UserBindServiceImpl](../src/main/java/top/aiolife/record/service/impl/UserBindServiceImpl.java) 用 `getOne`，表中只有主键。平台变更也须纳入同一唯一性规则 |
| `notification_channel_config(user_id, channel)` | [FeishuNotificationServiceImpl](../src/main/java/top/aiolife/record/service/impl/FeishuNotificationServiceImpl.java) 的 `saveConfig` 先 `findConfig` 再插入，无对应唯一键；并发首次保存可得到两条配置，后续 `selectOne` 无法确定一条 |
| `notification_preference(user_id, biz_type, channel)` | 同一服务 `updatePreferences` 先查后插入；事务没有消除首次插入竞态，表中无对应唯一键 |

建议复用当前 `user` 手机号/微信、`membership_provider.code` 已采用的有效记录模式：`active_flag` 由 `is_deleted=0` 派生为 1，删除后为 NULL，再将业务唯一键与 `active_flag` 组合。MySQL 唯一索引允许可空列出现多个 NULL，因此可以保留多条已删除历史记录。不能简单改成 `(业务键, is_deleted)`，否则第二条同键删除记录仍会冲突。[MySQL 5.7 唯一索引说明](https://docs.oracle.com/cd/E17952_01/mysql-5.7-en/create-index.html)

前置工作：查出有效重复与异常删除值，按业务规则处理；确定字符串比较规则；为并发重复返回明确业务错误。不要自动删除重复数据。

不要把所有缺唯一键的表都判断为同一缺陷：`notification_delivery` 当前入队已有 Redisson 事件锁及事务可见性处理；`system_config` 的普通管理入口只更新已有项。两者仍需明确数据库层唯一策略，但本次没有证明它们存在同样的无锁首次插入路径。

### D02：派生时长的维护存在缺口

`time_record.duration` 是 `end_time - start_time + 1` 的派生值。当前语义是 **0～1439 的分钟闭区间**，例如 09:00～09:59 共 60 分钟；不能改成简单相减。

[TimeRecordSaveReq](../src/main/java/top/aiolife/record/pojo/req/TimeRecordSaveReq.java) 的起止时间可省略；[TimeRecordServiceImpl.updateTimeRecord](../src/main/java/top/aiolife/record/service/impl/TimeRecordServiceImpl.java) 只在请求同时带起止时间时计算 `duration`，随后按非空属性更新实体。由此存在静态可推导的错误路径：已有 `start_time=540,end_time=599,duration=60`，只提交 `startTime=550`，起点改变而时长仍为 60，实际应为 50。本次未通过接口运行复现。

建议先读取并合并旧记录，再校验日期及 `0 <= start_time <= end_time <= 1439`，最后统一计算时长；或者将该接口明确为完整替换并强制起止值必填。若保留物理 `duration`，必须禁止独立写入并覆盖所有写入口；若改为查询派生/生成列，需同步当前查询和导出。

另有注释漂移：DDL 的起止时间写“0-1440”，实现却截到 1439。应随整改一起修正，不能让两个区间约定并存。

### D04：命名不统一已超出风格问题

以下为审查时快照；排序、普通备注和启用已按第 3.1 节整改。

需要优先处理语义容易误读的几组：

- `sys_menu.status` 为 **1 启用、0 禁用**，`sys_dict_type/sys_dict_data/user_dict_type/user_dict_data.status` 却为字符 **'0' 正常、'1' 停用**；`enabled`、`is_enabled` 又用于相同开关概念。只改字段名、不转换旧值会把状态翻转。
- `time_record.duration`、`performance.duration` 为分钟；`b_video.duration/watched_duration` 为秒；日志 `duration_ms` 为毫秒。同名不是同单位，统计或复用组件不能直接相加。
- `file.file_name` 实际是对象键，`data_export_job.file_name` 是下载文件名；`file.file_type` 与 `storage_object.content_type` 都表示 MIME。对象键、展示文件名、扩展名和 MIME 必须区分。
- `goal.start_date/end_date`、`task.due_date`、`performance.performance_date` 实际是 DATETIME；`device.purchase_date`、`income.inc_date` 为 DATE。命名不能掩盖精度差异，也不能为了改名把已有日粒度数据伪造为准确时刻。

具体目标术语见第 3 节，现有字段逐业务迁移，不做全库字符串替换。

### D05：文件模型职责需要收敛

[VideoCoverService.complete](../src/main/java/top/aiolife/record/service/VideoCoverService.java) 将 `storage_object.object_key/file_size/content_type/sha256` 复制到 `file.file_name/file_size/file_type/hash_value`。这是确认存在的重复存储。

但[FileServiceImpl](../src/main/java/top/aiolife/record/service/impl/FileServiceImpl.java) 的普通上传直接维护 `file`，未必有 `storage_object_id`；普通上传的 `hash_value` 还会写空字符串，而视频封面保存 SHA-256。现在不能简单删掉 `file` 的这些列。

建议方向：物理字节元数据由 `storage_object` 管理，业务归属、权限和附件关联由 `file` 管理。实施前先决定是否将普通上传也接入物理对象表；若保留投影，应写清唯一来源、写入责任、不可变约束和校验办法。哈希统一说明算法，不能让 `hash_value` 同时含空字符串、MD5 约定和 SHA-256 实值。

`file.biz_id` 为 BIGINT，只能关联相应类型的业务主键；`time_record.id` 为 UUID 字符串，当前不能直接接入这种反向关系。无需为了假设的附件需求扩大所有 ID 类型，但必须在新增附件业务前明确这一边界。

### D07：空值和注释没有形成完整契约

2026-10-28 已将这部分调整按用户要求合入全量基线；去重后涉及 44 张表、154 个字段。唯一已有库已只读确认完成对应结构调整，原独立对齐脚本已删除。完整接入状态及其他剩余差异集中见[数据库初始化与验证](数据库初始化与验证.md#已有库首次接入)，不能据此认为全部结构已一致。

- 原先 26 张表的 `is_deleted` 可空，而查询通常按 `is_deleted=0` 过滤；写入 NULL 会得到既非正常可见、又非明确已删除的数据。当前定义为 `TINYINT NOT NULL DEFAULT 0`。收紧此类约束前必须检查全部目标字段，遇到 NULL 或非 0/1 删除值时停止，不自动回填。
- `goal.user_id`、`b_video.user_id` 已收紧为 NOT NULL，服务端创建路径已有归属赋值；收紧归属约束时遇到包括软删除记录在内的空归属必须停止。`honor_category/wardrobe_category.user_id=NULL` 表示公共分类，以及匿名日志允许空用户，属于不同语义，继续保留。
- 公共分类范围也不统一：`time_tracker_category`、`user_dict_data` 使用 `user_id=0`，另两类分类使用 NULL。近期先在字段字典明确各自约定；将来统一时须同步可见性、覆盖与删除规则，不能把 0 当真实用户或把所有 NULL 当脏数据。
- 已补齐 128 处 COMMENT，包括 `exercise_record.exercise_count`、`income.tax`、`expense.exp_desc/transaction_id/counterparty_acct`，以及 `storage_object`、`image_import_task` 的全部列；补入业务含义、单位、枚举与空值语义。第 6 节保留修改前的统计以便追溯。

本次未调整字段名、索引、请求/响应或客户端契约。实体仍以 `Integer` 映射删除标记、`Long` 映射用户归属；创建归属已由服务端设置，Java 与两端类型无需改变。其他已非空的 `INT is_deleted` 仅按需补注释，未扩大为全库类型重写。

仓库规范记录目标环境为 MySQL 5.7.44，CI 为 8.0，本次未重查运行版本。5.7 不执行 CHECK 检查，不能把 DDL 中的 CHECK 当成目标环境已有保障；这些规则需要由服务层有效校验，并分别验证版本适用性。[MySQL 5.7 CHECK 说明](https://docs.oracle.com/cd/E17952_01/mysql-5.7-en/create-table.html)

### D08：先确定业务含义，再判断冗余

`goal.year/month/day` 与 `start_date/end_date` 都能由请求写入，[GoalServiceImpl](../src/main/java/top/aiolife/record/service/impl/GoalServiceImpl.java) 没有建立二者一致性规则。它们可能分别代表“归属周期”和“实际计划执行区间”，不能无条件从开始时间推导归属年份。建议：若确实独立，明确命名为周期字段并校验合法组合；若没有独立用途，保留日期区间并移除多余年月日。原来的 `goal.progress` 已不在基线中，不再列为待删字段。

`read_record.total_progress/current_progress` 可以是页数或百分比；`movie` 同名字段可以是集数或时长。当前没有独立单位列，`total_progress=100` 无法单靠数值判断是 100 页还是百分比制。建议明确 `progress_unit` 及对应范围，或固定每种业务类型的单位；不要为了“统一进度”把所有数量都改成百分比而丢失原始页数/集数。

### D09：当前结构必须能被重建和验证

当前结构由冻结的 B 基线和全部适用 V 迁移共同定义，执行顺序、历史与校验和由 Flyway 管理。日常只新增 V；用户选定时间节点后生成完整的新 B，并保留已有库需要的升级路径。117 已有库已按用户确认将历史执行边界登记至 `20261028.06`，现有脚本不得重跑。实际结构差异保留并独立跟踪，登记不表示差异已修复；未来修正必须新增更高版本 V。未知库仍须先核对结构与接入条件。

真实结构比较由 Java `SchemaTool` 和 v5 契约完成，比较表、列、索引、外键、CHECK 及 COMMENT；SQL 和迁移配置变化要求重新生成契约，工具源码摘要只作追溯。MySQL 5.7 不提供 CHECK 执行保障，接入时须明确处理这一平台限制。当前命令、目录和验证边界统一见[数据库初始化与验证](数据库初始化与验证.md)，本页不另存执行清单或测试流水。

[CurrentSchema](../src/test/java/top/aiolife/support/CurrentSchema.java) 用于构建 H2 单元测试结构，不代替真实 MySQL 验证。[PhysicalTableEntitySelectIntegrationTest](../src/test/java/top/aiolife/database/PhysicalTableEntitySelectIntegrationTest.java) 检查实体全字段查询，不能反向证明数据库没有多余列；实际结构仍需单独预检。迁移测试分别覆盖新库、已有库和追加结构迁移。

## 3. 共享字段语义与目标命名

这是后续设计使用的术语表；“目标名称”不表示已改列。同一语义统一名称，不同语义保留业务限定词。类型、长度、NULL、默认值及当前物理名称以逐表文档为准。

实体与 API 不要求通过数据库列改名一次性改完所有业务，但**同一次迁移涉及的业务只维护新的当前契约**，不引入旧字段双写或长期兼容分支。

## 5. 整改顺序与持续维护

1. **正确性先行**：处理 D01 唯一性与 D02 时迹派生值；在迁移前只读检查重复、空值与区间异常，实施时补有意义的并发和局部更新验证。
2. **清理存储职责**：处理 D03；同时修改业务、导出和 Query 所依赖的当前结构。确认现有数据去向后再删列，避免只凭实体未映射就删数据。
3. **分业务统一字段**：先排序/启用/备注等同义概念，再处理文件、金额、日期和单位。每批明确旧名、新名、值转换、关联方与验收范围；不把所有 `status/type/name` 一概统一。
4. **补约束与性能证据**：收紧必填语义、补 COMMENT、验证候选索引和目标 MySQL 版本；不能用“代码通常会填写”替代数据库设计。
5. **补完整初始化验证**：基线、尚未合并增量和当前实体必须可收敛到同一结构，分别记录隔离验证与目标环境执行结果。
