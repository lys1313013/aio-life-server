# 表结构还需要优化什么

核对日期：2026-11-13。

**现有表不用推翻重做。接下来主要是：删掉重复信息、补上防止错误数据的规则、统一含义不清的字段。**

建议先修衣柜分类删除和敏感信息存储，再处理文件重复信息及数据库校验。字段改名、删索引可以后做。

以下区分未完成事项与已经交付代码、已记录实际库迁移的事项，不将数据库迁移视为线上应用已部署。

## 先修可能影响数据正确性和安全的问题

### 1. 衣柜分类删了，下面的内容怎么办

涉及 `wardrobe_category` 和 `wardrobe_item`。

现在删除一个分类时，没有检查它下面是否还有子分类或衣物。例如删除“上装”，它下面的“衬衫”还在，但分类树可能不再显示“衬衫”；衣物也可能找不到原分类名称。

**建议：有子分类或衣物时先禁止删除，提示用户先移走内容。** 这主要需要修改删除逻辑，单纯给表加字段解决不了。

另外，系统消息现在把发送人写死为用户 `1`，但不能保证系统里有这个用户。应明确表示“系统发送”，不要借用一个未经保证存在的用户编号。

代码：[分类删除](../src/main/java/top/aiolife/wardrobe/service/impl/WardrobeCategoryServiceImpl.java)、[系统消息](../src/main/java/top/aiolife/record/notification/SystemNotificationSender.java)。

### 2. 敏感信息的保存方式需要统一

涉及 `api_key`、`user_bind` 和 `password_vault`。

现在 API Key 和第三方账号 Token 在数据库中保存原文。密码库的“账号”字段是另一种问题：契约为明文（用于列表展示与复制），Web 已按明文保存，移动端仍在加密写入；两端读取时还要按十六进制特征判断是否为旧密文。

**建议：API Key 只保存用于核验的摘要；第三方 Token 加密保存；密码库账号统一为明文，移动端改为明文写入并移除两端对旧密文的判断，密码和备注继续由客户端加密。** API Key 摘要不能还原出原文，所以完整 Key 只在创建时展示一次；第三方 Token 需要实际使用，服务端仍需能解密。这一项要连同现有数据和两端代码一起改。

代码：[API Key](../src/main/java/top/aiolife/sso/service/impl/ApiKeyServiceImpl.java)、[第三方绑定](../src/main/java/top/aiolife/record/service/impl/UserBindServiceImpl.java)、[Web 密码库](../../aio-life-front/apps/web-antd/src/views/password-manager/PasswordModal.vue)、[移动端密码库](../../aio-life-mobile/src/pages/vault/index.uvue)。

## 再整理表里重复或含义不清的信息

### 3. 附件四表已完成实际库升级与本地接口验收

`storage_object` 统一保存字节、对象键、SHA-256、大小、MIME 和图片尺寸；`attachment` 保存拥有者、用途、业务绑定和展示文件名；`external_resource` 保存共享来源，`import_job` 保存业务导入请求。成功来源持续复用，不设缓存过期或主动刷新，失败允许重试。

本次新增 `V20261116_10`、`V20261116_11` 及独立准备工具。2026-11-16 实际数据库完成备份、恢复校验和升级，原 296 条文件记录全部保留，本地后端通过 20 项真实接口检查；线上应用未更新。执行入口与历史异常文件说明见[附件四表升级](数据库初始化与验证.md#附件四表升级)，业务规则见[附件与来源表设计](附件与来源表设计.md)。

### 4. 一些明显不合理的值，数据库还没有拦住

例如银行卡账单日只能是 1–31，但数据库的这个字段本身可以存入 `40`。正常页面和接口已有日数校验，数据库还缺少同样的限制。

类似情况还有：部分业务的结束日期可以早于开始日期，以及“是否删除”字段可能存入 0、1 之外的数字。

**建议：给这些已经明确的规则补数据库校验。** 这样即使脚本或某个写入入口漏了检查，也不能保存错误值。已有数据要先检查，不能自动猜测怎么修。

金额和进度不能直接套规则：退款是否允许负数、重复观看的累计时长是否允许超过视频长度，要先确定业务含义。

结构：[当前建表脚本](../sql/migrations/V20261110_01__postgresql_schema.sql)。

### 5. 进度和目标日期的含义还不够明确

涉及 `read_record`、`movie` 和 `goal`。

阅读进度里的 `100`，可能表示 100 页，也可能表示 100%；影视进度也可能按集数或时长记录，但表里没有单独说明单位的字段。只看数字，无法知道应该怎么展示和统计。

目标表同时有“年/月/日”和“开始/结束时间”。例如“2026 年目标”能不能安排在 2027 年完成，目前还没有明确二者的关系。

**建议：进度明确记录单位；目标明确区分“归属哪个周期”和“计划何时执行”。** 旧记录不能只凭数字自动猜单位，也不能直接删掉一组日期。

### 6. 日期字段和代码使用的类型不一致

涉及 `event_record.event_date`。

活动日期在数据库里能存到几点几分，代码却只按年月日读写，时间部分无法完整往返。

**建议：活动如果只需要年月日，就让数据库也只存日期；如果需要开始时刻，就让代码完整读写时刻。** 先检查已有数据，避免丢掉已经保存的时分秒。

里程碑已于 2026-11-16 将实体、请求和响应的日期统一为 `LocalDate`，Java／JSON 字段使用 `date/endDate`，数据库保留 `date/end_date`；Web、移动端及生成契约同步使用 `endDate`，不再作为待办。

## 最后按数据量安排性能和维护优化

### 8. 日志需要明确保留多久

涉及登录日志、API 调用日志、邮件日志、操作日志、定时任务日志和通知投递记录。

这些表会持续增加记录，但目前没有统一的保留期限和定期清理安排。长期不处理，存储、备份和查询成本都会增加。

**建议：按用途确定保留时间，再增加分批清理。** 审计记录和普通运行日志可能需要不同期限，不建议现在直接一刀切删除。

字段改名、删除可能重复的索引，以及把附件逐条查询改为批量查询，可以随对应业务后续处理。它们不都需要改表，也不能只凭旧报告就直接删字段或索引。统一 Y/N 与 0/1 已由 `V20261116_05` 处理。

## 3. 共享字段语义与目标命名

这是后续设计使用的术语表；“目标名称”不表示已改列。同一语义统一名称，不同语义保留业务限定词。类型、长度、NULL、默认值及当前物理名称以逐表文档为准。

## 3.3 文本排序规则与大小写（2026-11-12）

普通业务文本列使用数据库默认确定性排序规则，机器标识的 `COLLATE "C"` 例外见下文。数据库默认排序规则是确定性的，按字节精确比较：大小写、重音和全半角不同的值不相等，唯一索引不会折叠。

- 大小写不敏感只在查询层显式表达：模糊匹配使用 `ILIKE`（后端封装为 `IlikeQuery.anyOf`），等值匹配使用 `lower(col) = lower(?)`。
- `sys_user.username`、`sys_user.email` 的有效记录唯一索引基于 `lower(col)`，登录、注册查重、找回密码的查询使用相同表达式。
- 机器标识（路由、键、编码、幂等键和外部标识）需要与数据库 locale 无关的固定字节序时显式使用 `COLLATE "C"`；同一语义的关联列必须同步，避免跨列比较报错。当前使用 `"C"` 的列见[数据库表结构](数据库表结构.md#文本排序规则与大小写)。
- 数据库默认排序规则由建库参数决定（PostgreSQL 18 默认 builtin `C.UTF-8`），排序结果不承诺中文拼音序；需要拼音序的查询显式写 `COLLATE "zh-x-icu"`。

## 3.4 公共预设与用户覆盖（2026-11-16）

系统预设与用户数据统一由 `user_id` 区分，不再使用 0 号用户或独立模板表：

- `user_id IS NULL` 表示系统公共预设，`user_id = 实际用户ID` 表示用户数据；列可为空，并以 `CHECK (user_id IS NULL OR user_id > 0)` 禁止 0 写入。
- 用户改写或隐藏预设时新建一行，`template_id` 指向预设 ID；用户自建项的 `template_id` 为空。覆盖行只保存与预设不同的展示值，未填字段继承预设。
- 预设不可由用户删除或改名；接口返回派生的 `preset` 布尔，不暴露 `user_id` 或哨兵值。
- 预设行的 `create_user/update_user` 为空，表示系统维护。
- 预设与用户项分别建索引：预设使用 `WHERE user_id IS NULL AND is_deleted = 0` 的部分索引，用户项使用 `(user_id, ...)`。
- 适用表：`time_tracker_category`、`user_dict_data`、`wardrobe_category`、`honor_category`；`sys_dict_data` 等全局参考字典不套用此规则。
- 缓存键不接受 null，公共预设使用固定键 `preset`；0 不再具有任何数据库或缓存语义。

| `bank_card.bank_id/custom_bank_name` | 保留互斥来源；字典银行与自由填写是两个入口，不是双写。服务层须验证二选一，不能只依赖 CHECK |
| `sys_user.active_flag` / `membership_provider.active_flag` | 保留。生成列服务于有效唯一约束，由数据库派生，不是用户可编辑状态 |
| 日志 `user_id/username/nickname` | 可以保留当时快照，避免账号改名后日志失去原上下文；在日志契约中说明快照时点 |
| `b_video.cover/cover_state/cover_version` | 已于 2026-11-16 通过 `V20261116_11` 从实际库删除；来源在 `external_resource`，请求状态在 `import_job`，附件发布由业务记录锁及有效任务条件控制，不保留业务版本列。线上应用仍需配套更新 |
| `b_video.pages_info/episodes/current_episode/watched_duration_seconds` | 不按表面相似删除。分集元数据、总集数、当前位置及累计观看量不是一回事；如总集数从元数据派生，应选定写入来源和一致性规则 |
| 关联表 `user_id` | 可作为有意冗余保留，便于隔离和按用户查询；例如 `device_expense`、`bank_card_tag_rel`，写入必须验证两端对象均属同一用户 |
| `life_footprint.city/region_code/coordinate_system` | 不直接删除。地点来源城市名与选定地区编码未必等价；坐标系显式标记可避免误读，当前只允许 GCJ02。若决定派生城市名，应先定义地区版本与历史展示规则 |
| `data_export_job.status/artifact_status` | 保留。任务执行终态和导出文件过期/撤销/删除是独立生命周期，不能合成一个状态 |

`sys_dict_type`、`sys_dict_data` 的 `is_enabled` 为 `NOT NULL DEFAULT 1` 并带 0/1 检查；`user_dict_data.is_enabled` 保持可空，`NULL` 表示继承公共值。
