# 状态字段语义化评估与迁移清单

> 目标：让业务状态在 API、MCP 和必要的持久化场景中使用稳定、可读的语义 code，避免让调用方理解无上下文的 `0/1/2/3`。
>
> 本文档只处理具有三个及以上取值的业务状态字段，不扩展到 `type`、`priority`、`level` 等非状态枚举。AI 面对的是 API/MCP 契约，不是数据库；仅为 AI 可读性，优先在 DTO/MCP 边界转换。

## 统一原则

- 新增语义 code 使用 **lower_snake_case**，例如 `in_progress`。
- 状态 code 表达通用生命周期，不携带页面展示文案。`reading/watching`、`finished/watched` 不应成为两套底层状态。
- 中文文案由前端或服务端视图层根据业务场景映射，文案变化不应引发数据库迁移。
- Java 侧对新迁移字段使用枚举，显式配置持久化 code（如 `@EnumValue` 或 `IEnum<String>`），不依赖 `Enum.name()` 隐式推导。
- 若使用字符串列，使用 `varchar(32)` 并增加 `CHECK` 约束；不使用 MySQL 原生 `ENUM`。
- 已稳定运行的大写字符串枚举不因格式统一而迁移。

## 一、通用生命周期状态

`goal`、`read_record` 和 `movie` 共用同一套四态生命周期 code：

| 状态 code | 通用语义 | 阅读展示 | 观影展示 | 目标展示 |
|---|---|---|---|---|
| `not_started` | 尚未开始 | 想看 | 想看 | 待开始 |
| `in_progress` | 正在进行 | 在看 | 在看 | 进行中 |
| `completed` | 已完成 | 看过 | 看过 | 已完成 |
| `on_hold` | 暂停/搁置 | 搁置 | 搁置 | 搁置 |

> 阅读主页、编辑抽屉与时迹关联记录选择器统一展示“想看 / 在看 / 看过 / 搁置”。这些文案是 UI 契约，不影响底层状态 code 设计。

### 实施映射

| 表 | 字段 | 当前编码 | 建议语义 code |
|---|---|---|---|
| `goal` | `status` | 0=待开始，1=进行中，2=已完成，3=已放弃 | `not_started` / `in_progress` / `completed` / `on_hold` |
| `read_record` | `status` | 0/1/2/3 | `not_started` / `in_progress` / `completed` / `on_hold` |
| `movie` | `status` | 0/1/2/3 | `not_started` / `in_progress` / `completed` / `on_hold` |

`b_video.status` 同样复用 `ProgressStatusEnum`。B站页面将 `on_hold` 展示为“已暂停”；原“部分完成”与“进行中”语义重叠，历史值统一迁移为 `in_progress`：

| 当前编码 | 当前语义 | 建议语义 code |
|---|---|---|
| 1 | 未开始 | `not_started` |
| 2 | 进行中 | `in_progress` |
| 3 | 已暂停 | `on_hold` |
| 4 | 部分完成 | `in_progress` |
| 5 | 已完成 | `completed` |

### B. 不纳入范围的非状态枚举

- `goal.type`、`read_record.type`、`movie.type`
- `task_detail.priority`
- `message.type`
- `honor_record.level`
- `time_tracker_category.time_type`
- `time_record.relate_type`
- `wardrobe_category.category_type`

这些字段继续保持现有契约。只有出现明确的接口可读性、扩展性或业务一致性问题时，才按各自业务模块单独立项评估。

### C. 保持现状的二态字段

两态且无扩展需求的字段继续使用 `0/1`。将 `0/1` 改为 `enabled/disabled` 不会带来足够收益，反而会破坏现有管理端契约。

`sys_menu.status`、`sys_dict_type.status`、`sys_dict_data.status`、`user_dict_type.status`、`user_dict_data.status`、`mail_log.status`，以及 `is_deleted`、`is_read`、`is_default`、`is_top`、`is_public`、`is_completed`、`is_enabled`、`enabled`、`favorite`、`hidden_content`、`is_pinned`、`is_starred`、`auto_renew`、`is_manual`、`is_track_time`、`is_special`、`is_readonly`。

> `user_dict_data.status` 还参与公共模板隐藏与用户覆盖合并，不是普通展示字段，不应在通用批次中迁移。

### D. 已有稳定字符串契约，不做纯格式迁移

以下字段虽然使用大写枚举值，但已被 Java、前端和历史数据稳定使用：

- `feedback.status`、`feedback.feedback_type`、`feedback.priority`
- `feedback_comment.role_type`
- `notification_delivery.status`
- `notification_channel_config.channel`、`notification_preference.channel`
- `system_config.config_type`

仅将 `PENDING` 改为 `pending` 没有增加语义，但会造成破坏性契约变更，因此保持现状。如未来确定全项目必须统一 lower_snake_case，应作为独立专项迁移。

### E. 用户字典与外部原始值

- `device.status` 来自 `device_status` 用户字典，不应在代码中固定为 `in_use/idle/retired/sold`。如需将 `varchar(255)` 收窄为 `varchar(32)`，必须先盘点真实 `dict_value` 长度。
- `expense.transaction_status` 来自第三方账单导入，保留原值；如有统计需求，另增内部规范化字段或在导入层映射。

## 四、安全迁移要求

### 迁移前

1. 对目标列执行 `GROUP BY` 统计，确认所有真实值、`NULL` 数量和默认值。
2. 明确未知值的处理方式；禁止使用无 `ELSE` 的 `CASE` 将未知数据静默改为 `NULL`。
3. 记录原列的类型、可空性、默认值、注释、索引和行数，准备回滚 SQL。

### 上线方式

优先使用可兼容的影子列方案：

1. 新增 `<field>_code` 字符串列。
2. 回填并校验新旧值一一对应。
3. 应用短期双写，读取优先使用新列并兼容旧列。
4. 前后端契约切换完成后，停止旧列写入。
5. 观察稳定后再删除旧列。

如确定使用维护窗口原地修改列，必须在停止旧版本写入后执行，并在服务恢复前完成数据校验。

### 迁移后

- 校验总行数、各状态数量、`NULL` 数量和未知值数量。
- 校验列表默认排序、状态筛选、状态统计和自动流转。
- 校验 REST 与 MCP 响应，确保 code 和中文 label 边界清晰。
- 校验新旧版本不会向同一列写入两种格式。

## 五、首批实施结果

1. `goal.status`、`read_record.status` 和 `movie.status` 已在代码中统一使用 `ProgressStatusEnum`。
2. REST 请求与响应使用统一状态 code，MCP 查询参数使用 code、响应继续输出对应场景的中文 label。
3. 阅读、观影主页、编辑抽屉与时迹关联选择器统一展示“想看 / 在看 / 看过 / 搁置”；目标展示“待开始 / 进行中 / 已完成 / 搁置”。
4. 已提供 `2026-09-06_stringify_progress_status.sql`，用于在维护窗口将三张表现有 `0/1/2/3` 原地迁移为语义 code；脚本需在目标环境盘点数据后执行。
5. `b_video.status` 已完成代码改造并复用 `ProgressStatusEnum`，历史“部分完成”在迁移时并入 `in_progress`；数据库执行完成后结束本专项。荣誉等级、任务优先级、业务类型等非状态枚举不在改造范围内。
