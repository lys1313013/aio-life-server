# 个人菜单显示设置

入口：个人中心 → 菜单显示。勾选需要展示的菜单，分组勾选作用于当前子项，点击保存后更新导航及菜单搜索；恢复默认清除当前用户的所有隐藏记录。

## 行为边界

- 管理员的启用状态、角色授权和系统隐藏设置优先；用户只能调整当前有权配置的菜单。
- 仅影响导航展示。完整授权路由仍注册，隐藏页面的 URL、刷新和已打开标签页继续可用；菜单锁、业务数据、任务与用户快捷导航保持原行为。
- 子菜单全部隐藏时，空父分组自动消失。仅保存末级展示项 ID，新增菜单默认显示；`hideChildrenInMenu` 的单入口菜单按一个展示项处理。
- 个人中心不允许隐藏，头像菜单中的个人中心入口仍可用于恢复设置。
- 设置按账号存储；重新加载页面或登录时读取后端。同账号其他已打开页面需刷新后读取最新设置。
- 登录初始化读取偏好失败时，提示错误并暂时展示系统默认导航，不阻断登录；设置页加载失败时只允许重试，不能误保存空设置。
- 设置页始终返回可配置的完整菜单树，包含个人隐藏的项。管理员停用、删除或撤权的菜单不出现在设置列表；保存时校验当前权限，拒绝非法 ID。
- 保存为全量替换；同账号并发保存由用户行锁串行执行，以最后一次成功保存为准。保存时清理不在新集合中的历史记录，恢复默认清除全部历史隐藏记录。

## 表与删除方式

`user_menu_hidden` 继承 `BaseEntity`，包含完整审计字段与 `is_deleted`，唯一索引为 `(user_id, menu_id)`。新记录 `is_deleted = 0`，不写入逻辑删除记录。

保存发生变化时，在事务内按用户物理删除旧集合并插入新集合；相同集合不重复写入。恢复默认直接物理删除当前用户记录。`UserMenuHiddenMapper.physicalDeleteByUserId` 使用显式 `DELETE FROM user_menu_hidden WHERE user_id = ...`，不使用 `BaseMapper.delete*`。

## API

接口均使用登录态用户 ID，不接受客户端指定用户 ID。路径包含服务 context-path `/api`。

| 方法 | 路径 | 用途 |
|---|---|---|
| GET | `/api/menu/preferences` | 获取可配置菜单树和隐藏 ID |
| PUT | `/api/menu/preferences` | 保存全量隐藏 ID |
| DELETE | `/api/menu/preferences` | 恢复默认 |

PUT 请求示例，所有菜单 ID 在前端使用字符串：

```json
{"menuIds":["1501","1503"]}
```

空数组恢复全部显示；缺失或 null 的 `menuIds` 会被拒绝，不视为清空。最多接受 2000 个 ID，重复 ID 自动去重，目录与不可配置菜单 ID 会被拒绝。

三个接口都返回 `{ "rscode": "0", "data": { "menus": [...], "hiddenMenuIds": [...] } }`，菜单节点包含 `id`、`title`、`children`，所有 ID 均为字符串。

## 发布与验证

先执行 `sql/1_init_table/2026-09-26_add_user_menu_hidden.sql`，再发布后端和前端。前端登录初始化会读取新接口，发布前必须准备好表与后端。

验证重点：不同账号隔离；隐藏后侧边栏/菜单搜索消失但直接 URL 仍可访问；刷新保留；恢复显示与默认设置；分组全隐藏；新增菜单默认显示；管理员授权变更；手机、平板、桌面及暗色主题。

针对性测试：后端 `UserMenuPreferenceServiceTest`；前端 `menu-visibility.test.ts`、`menu-display-setting.test.ts`。
