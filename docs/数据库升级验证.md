# 数据库升级验证与发布前结构预检

脚本格式、表/字段注释、索引/约束说明和迁移文件头遵循 [SQL 脚本规范](SQL脚本规范.md)。

继续使用单体应用和现有 SQL 迁移；不在应用启动时自动修改生产库。`sql/upgrade-plan.json` 固定旧版本、旧全量结构摘要和本次增量脚本顺序/摘要，CI 验证升级结果后才允许发布镜像。

## 两条互补验证路径

- 原有测试任务：最新全量结构创建新库，运行 Maven 测试及打包。
- 新增 `database-upgrade` 任务：MySQL 8.0 隔离服务中，从 `64156465fe8eae58c79f21cd42153766358178f1` 的结构创建旧库，插入明确的合成账号、银行卡及系统菜单，再依次执行计划内迁移。另建最新全量结构的新库，比较全部表、列类型/可空性/默认值/生成表达式、索引、CHECK 和外键。列位置和注释不影响比较。

升级验证还检查旧账号及卡号字段没有被改写、旧账号不被自动绑定手机号/微信、新管理菜单可用、手机号/openid 唯一性、半个手机号约束、逻辑删除后重新注册，以及卡号可空。头像迁移另验证旧 URL 不保留、avatar 列已删除、文件绑定可清除，且引用中的文件受外键保护。约束负例必须返回预期的 MySQL 约束错误，连接或 SQL 语法失败不会被误判为约束通过。

PR 会运行上述两条路径；镜像发布同时依赖两者成功，PR 不发布镜像。新库初始化后不要再次执行微信增量 ALTER，它不是幂等脚本。

## 本地验证

先启动**独立测试 MySQL 8.0**，不要复用生产服务。Python 仅用标准库，需安装 `mysql` 客户端；密码通过 `MYSQL_PWD` 环境变量提供，命令行和报告不写密码。脚本禁用客户端默认配置，连接参数必须明确提供。

```sh
python3 scripts/test-database-upgrade.py
python3 scripts/check-database-upgrade.py --host 127.0.0.1 --port 3307 --user root verify
```

验证器只创建及删除自身随机命名的 `aio_upgrade_*` / `aio_fresh_*` 临时库，先剥离历史脚本中指向 `aio_life` 的建库/切库语句并拒绝其他切库指令。基线 Git 对象必须存在（CI 使用完整历史）；应用库不会被初始化或清空。进程被强制终止时可能遗留临时库，按当次输出/实例记录人工确认后清理。

成功产物在 Git 忽略的 `artifacts/database-upgrade/`：

- `upgrade-report.json`：实际 MySQL 版本、基线、迁移顺序/摘要和验证结果。
- `schema-contract.json`：该版本完整的预期结构快照，仅包含元数据。

CI 将二者作为 `database-upgrade-<commit SHA>` 工件保留 30 天。发布时将工件与镜像版本一起归档；本地非 MySQL 8.0 的结果只能作为补充，不替代 CI MySQL 8.0 的结果。

## 已有数据库发布流程

1. 核对实际已执行迁移，备份数据；按计划中的顺序执行**尚未执行**的增量脚本。更早版本先补齐到计划基线，不能把本计划当作任意历史版本的一键升级器。
2. 保存部署执行记录，至少包含镜像/提交 SHA、各 SQL 文件及 SHA-256、执行时间、执行人、结果与备份编号。已执行脚本不要重复运行（下文明确可重复执行的平台预设目录除外）；历史迁移 checksum 变化必须人工调查。
3. 下载同一发布版本的 `schema-contract.json`，使用只读数据库账户执行预检：

```sh
python3 scripts/check-database-upgrade.py --host DB_HOST --port 3306 --user schema_reader \
  preflight --database aio_life --expected /path/to/release/schema-contract.json
```

`preflight` 只执行信息架构 SELECT；缺列、缺索引、约束未启用、字段或结构不匹配均以非零退出并给出元数据差异。它不执行迁移，也不验证业务数据、微信服务或运行时权限。目标账户需能查看全部应用表的元数据。附加备份/自定义表也会被报告为差异，需核实而非盲目删除。

4. 预检成功后再部署匹配镜像，并执行应用联调。保留预检输出；若结构尚未完成则停止发布。

## 后续增加迁移

更新全量结构的同时追加增量 SQL 和计划条目/摘要；先保持同一冻结基线，验证从该基线到最新的完整升级链。若要推进基线，必须同时评审已支持的升级范围、合成数据夹具以及迁移记录，不能只改基线来跳过失败迁移。全量结构与增量链不一致将由 CI 拦截。

## 菜单分端启用

`status` 控制 Web，`mobile_status` 控制移动端（H5、微信、App 共用）；`/menu/all`、`/menu/preferences`、`/quick-nav/candidates`、`/quick-nav/my` 通过 `client=web|mobile` 选择，缺省为 Web，非法值拒绝。管理接口返回全量菜单与两个状态；`PUT /menu/admin/{id}/status` 与 `PUT /menu/admin/{id}/mobile-status` 独立更新，均使用 `{ "status": 0|1 }`。旧客户端编辑未提供 `mobileStatus` 时保留原值，新增未提供时复制 `status`。

父级关闭会过滤该端后代入口，角色规则仍由后端校验。菜单锁根据未删除的完整菜单关系计算，不因任一端关闭入口而解除保护。移动端菜单目录在页面显示时重新校验，下拉刷新也可获取新配置；菜单写入后清除本地目录缓存。
