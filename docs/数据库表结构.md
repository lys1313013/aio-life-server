# AIO Life 数据库表结构

跨表字段语义、命名统一、冗余取舍和当前设计问题集中维护在[数据库设计审查与字段规范](数据库设计审查与字段规范.md)。本文只维护当前逐表结构，不把建议方案写成已实施契约。

本文档描述当前业务结构，由 `sql/migrations/B20261028_00_001__mysql_compatible_baseline.sql` 全量基线与 `sql/migrations/` 中尚未合并的适用增量共同定义。结构变更必须新增可执行的 Flyway `V` 迁移并同步本文档；已执行迁移不改写，用户在选定时间节点生成新的完整 `B` 基线。

新库初始化和已有库升级统一通过 `mvn -f tools/flyway/pom.xml compile flyway:migrate` 执行；执行流程、首次接入和版本限制见[数据库初始化与验证](数据库初始化与验证.md)。本页只描述业务结构，不另行维护 SQL 执行顺序。117 库已登记至 `20261028.06`，下述旧脚本用于说明目标结构及新库构造，不是对该库的待执行清单；实际差异须另增更高版本 V 处理。`flyway_schema_history` 是迁移工具管理的基础设施表，不属于下方业务表清单。

2026-10-28 已将空值约束与字段注释优化合入全量基线：26 张表的 `is_deleted` 为 `TINYINT NOT NULL DEFAULT 0`，`goal.user_id`、`b_video.user_id` 非空，补齐 128 处字段注释。唯一已有库的核对结果与剩余接入差异集中见[数据库初始化与验证](数据库初始化与验证.md#已有库首次接入)。下表“必填”表示数据库 NOT NULL，接口必填规则以 DTO 校验为准。

公共字段统一由 [V20261028_02__unify_common_fields.sql](../sql/migrations/V20261028_02__unify_common_fields.sql) 定义：排序 `sort_order`、普通备注 `remark`、启用 `is_enabled`（数字 1/0）；菜单保留 `web_is_enabled/mobile_is_enabled`，首页固定排序使用 `pinned_sort_order`。本增量尚未合并至全量初始化基线。

2026-10-28 采集来源的完整五字段结构由 [01 增量](../sql/migrations/V20261028_01__asset_purchase_source.sql)补齐；已有库的收支类型/非空约束、用户字典默认值/索引及废弃敏感日志列由 [03 增量](../sql/migrations/V20261028_03__schema_alignment.sql)按前置条件对齐。[04 增量](../sql/migrations/V20261028_04__schema_comments.sql)补齐空注释并纠正已核实的旧语义，保留其他字段属性。实际接入状态见[数据库初始化与验证](数据库初始化与验证.md#已有库首次接入)。本文描述执行适用增量后的当前契约，不代表目标业务库已完成升级。

统一约定：

- 新建结构：数据库 `aio_life`，表使用 **InnoDB** 引擎及 **utf8mb4 / utf8mb4_unicode_ci**；特定标识字段的排序规则以逐表定义为准。既有库增量可保留原表排序规则，需以结构预检结果识别差异，不能据此说明现存库已全部统一
- 逻辑删除：业务表统一包含 `is_deleted` 字段（0=未删除，1=已删除），由 MyBatis Plus 全局配置处理
- ID 生成：新表 ID 使用雪花算法（`IdType.ASSIGN_ID`）在应用层生成，部分历史表为 `AUTO_INCREMENT`
- 公共字段：审计字段名称使用 `create_user` / `update_user`（bigint）和 `create_time` / `update_time`（datetime，部分表为 datetime(3)）；可空性、默认值及自动更新时间以逐表定义为准。允许系统操作的表可将操作人留空，`bank_card` 等表的操作人仍为非空；审计时间也并非统一可空
- 例外：`api_key_log`、`login_log`、`mail_log` 为追加型日志表，`enum_type` 为枚举定义表，不要求完整审计字段及逻辑删除字段
- 例外：`sys_work_calendar` 为全局共享的日历基础数据表，使用 `calendar_date` 自然主键和 `updated_at` 更新时间，不使用雪花 ID、完整审计字段及逻辑删除字段
- 例外：`user_menu_hidden` 保留完整公共字段，`is_deleted` 固定为 0；恢复菜单显示与恢复默认使用物理删除

### sys_work_calendar —— 中国大陆工作日历表

记录中国大陆统一放假、调休安排，每个自然日一行，所有年份共用一张表，不包含个人排班、请假。日期按 `Asia/Shanghai` 解释。

| 字段 | 类型 | 必填 | 默认值 | 说明 |
|---|---|---|---|---|
| calendar_date | date | 是 |  | 日历日期，主键 |
| day_type | tinyint | 是 |  | 0=普通工作日，1=普通周末，2=节假日休息，3=调休补班 |
| holiday_name | varchar(50) | 否 | NULL | 关联节日名称，如春节、国庆节；普通日期为空 |
| source | varchar(50) | 是 |  | 数据来源，如 weekday_rule、holiday-cn、manual |
| updated_at | datetime | 是 | CURRENT_TIMESTAMP（ON UPDATE CURRENT_TIMESTAMP） | 最后更新时间 |

索引：PRIMARY KEY (calendar_date)。约束：`chk_sys_work_calendar_day_type` 限定 `day_type IN (0, 1, 2, 3)`（MySQL 8.0.16 起执行 CHECK 约束）。

工作日按 `day_type IN (0, 3)` 查询，非工作日按 `day_type IN (1, 2)` 查询，不冗余存储 `is_workday`、年份、月份或星期。类型 2 表示假期安排中的休息日，不用于判断法定节假日加班工资倍数。

建表定义集中于当前全量结构；年度默认日历通过初始化数据脚本导入。

2026 年初始化数据：`sql/migrations/V20261028_05_008__sys_work_calendar_2026.sql`。由 Flyway 在结构就绪后执行该迁移，可离线导入全年 365 天：普通工作日 242 天、普通周末 84 天、节假日休息 33 天、调休补班 6 天，合计工作日 248 天、非工作日 117 天。脚本仅补充缺失日期，重复执行保留已有记录及人工修改，不用于修正已有错误数据。

数据根据 [holiday-cn 的 2026 年 JSON](https://raw.githubusercontent.com/NateScarlet/holiday-cn/master/2026.json) 生成，并于 2026-09-22 与[国务院年度安排（北京市政府转载）](https://www.beijing.gov.cn/fuwu/bmfw/sy/jrts/202511/t20251104_4258838.html)逐条核对；源文件 SHA-256 记录在 SQL 注释中。

生成年度数据时先生成全年 365/366 个日期，按星期规则填充并标记 `source=weekday_rule`，再使用已公布的年度放假、补班数据覆盖日期类型并记录实际来源。应校验全年日期完整后保存；日期缺失表示尚未导入，不能直接视为工作日。跨年安排需结合相邻年份数据检查，本次检查的 `2027.json` 暂无安排，后续公告若影响 2026 年末日期需另行更新。

时迹分类推荐通过 `IWorkCalendarService.findPreviousComparableDate(date)` 查找严格早于目标日期的最近同类日：类型 0/3 归为工作日，类型 1/2 归为非工作日。例如 `2026-09-21` 参考补班日 `2026-09-20`，`2026-09-26` 参考假期日 `2026-09-25`，`2026-10-08` 参考 `2026-09-30`。历史高频及后续分类查询也关联日历表分组，未导入日历的历史日期不参与这些统计。

仅“指定日期 → 上一个同类型日期”的成功结果使用 Redis 缓存，key 为 `workCalendar:prevDate:YYYY-MM-DD`，value 为参考日期字符串，TTL 为 **2 天（172800 秒）**。缓存命中直接返回，空结果不缓存；普通 `isWorkday(date)` 判断直接查表，不缓存全年或日期类型。日历修正后，可调用 `evictPreviousComparableDate(date)` 清除受影响的目标日期缓存；直接执行 SQL 不会自动失效缓存，未清理时最多等待 2 天。

目标日期缺失时不推荐分类；参考日期缺失或候选日期到目标日期之间存在缺口时，跳过参考日推荐，仍可使用已知日期类型的历史高频分类。时间块计算与记录保存不依赖参考日期是否存在。部署前须先执行建表及年度数据初始化脚本；跨年参考需补充上一年日历。

验证：`WorkCalendarServiceImplTest` 覆盖放假、补班、跨年、闰日、日期缺口、按日缓存与清理；`WorkCalendarIntegrationTest` 通过显式指定的 `AIO_CALENDAR_TEST_MYSQL_PORT` / `AIO_CALENDAR_TEST_REDIS_PORT` 连接本地临时 MySQL/Redis，验证真实 Mapper SQL、缓存 TTL 和推荐链路，不读取正式环境配置。

## life_footprint 生活足迹

保存长期生活地点，起止日期使用 DATE，精确到日，不设置精度字段；`end_date` 必填，`9999-12-31` 表示至今。坐标统一为 GCJ02，ID 为字符串响应。不保存幂等键、版本或单独的至今状态；暂不使用乐观锁，`update_time` 仅用于审计。

```sql
CREATE TABLE IF NOT EXISTS `life_footprint` (
  `id` BIGINT NOT NULL COMMENT '足迹ID，由应用生成雪花ID',
  `user_id` BIGINT NOT NULL COMMENT '所属用户ID，用于用户数据隔离',
  `start_date` DATE NOT NULL COMMENT '开始日期，精确到日，格式YYYY-MM-DD',
  `end_date` DATE NOT NULL COMMENT '结束日期，9999-12-31表示至今',
  `place_name` VARCHAR(100) NOT NULL COMMENT '地点名称，可填写住所名称或自定义名称',
  `address` VARCHAR(500) DEFAULT NULL COMMENT '详细地址，可补充楼栋和房号，未填写时为空',
  `city` VARCHAR(100) DEFAULT NULL COMMENT '地点所属城市名称，未获取时为空',
  `region_code` VARCHAR(12) DEFAULT NULL COMMENT '所选最深层地区编码，可停在省市区县或乡镇，未选时为空',
  `longitude` DECIMAL(10,6) NOT NULL COMMENT '经度，GCJ02坐标，单位度，范围-180至180',
  `latitude` DECIMAL(9,6) NOT NULL COMMENT '纬度，GCJ02坐标，单位度，范围-90至90',
  `coordinate_system` VARCHAR(16) NOT NULL DEFAULT 'GCJ02' COMMENT '坐标系，固定为GCJ02，写入前须完成坐标转换',
  `provider_uid` VARCHAR(128) DEFAULT NULL COMMENT '百度地点UID，手动选点或未获取时为空',
  `remark` TEXT COMMENT '备注，未填写时为空，应用限制5000字符',
  `create_user` BIGINT DEFAULT NULL COMMENT '创建人用户ID，未记录时为空',
  `create_time` DATETIME DEFAULT NULL COMMENT '创建时间，由应用写入，未记录时为空',
  `update_user` BIGINT DEFAULT NULL COMMENT '最后更新人用户ID，未记录时为空',
  `update_time` DATETIME DEFAULT NULL COMMENT '最后更新时间，由应用写入，未记录时为空',
  `is_deleted` INT NOT NULL DEFAULT 0 COMMENT '逻辑删除标记：0=未删除，1=已删除',
  -- 应用生成的足迹ID全表唯一。
  PRIMARY KEY (`id`),
  -- 按用户和删除状态筛选，并按开始日期排序读取足迹。
  KEY `idx_footprint_user_start` (`user_id`, `is_deleted`, `start_date`),
  -- 统一存储GCJ02坐标，避免跨端地图坐标系混用。
  CONSTRAINT `ck_footprint_coordinate` CHECK (`coordinate_system` = 'GCJ02'),
  -- 经度必须处于有效范围，单位为度。
  CONSTRAINT `ck_footprint_lng` CHECK (`longitude` BETWEEN -180 AND 180),
  -- 纬度必须处于有效范围，单位为度。
  CONSTRAINT `ck_footprint_lat` CHECK (`latitude` BETWEEN -90 AND 90),
  -- 结束日期不得早于开始日期；9999-12-31表示至今。
  CONSTRAINT `ck_footprint_end` CHECK (`end_date` >= `start_date`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_unicode_ci COMMENT='生活足迹，记录长期居住地点';
```

## device_expense（设备支出关联）

一个设备支持多笔支出，每笔支出最多关联一个设备，无费用用途字段。`expense_id` 对已解绑记录也唯一；解绑将 `is_deleted` 置为 1，重绑复用同一记录，保留首次创建审计并更新修改审计。设备或支出逻辑删除时同步解除关联，另一侧业务记录保留。关联不改变设备购买价格。

```sql
CREATE TABLE `device_expense` (
  `id` BIGINT NOT NULL COMMENT '关联ID，由应用生成雪花ID',
  `user_id` BIGINT NOT NULL COMMENT '所属用户ID，用于数据隔离',
  `device_id` BIGINT NOT NULL COMMENT '关联设备ID',
  `expense_id` BIGINT NOT NULL COMMENT '关联支出ID，解绑后复用同一关联记录',
  `create_user` BIGINT DEFAULT NULL COMMENT '首次创建人用户ID，未记录时为空',
  `create_time` DATETIME DEFAULT CURRENT_TIMESTAMP COMMENT '首次创建时间',
  `update_user` BIGINT DEFAULT NULL COMMENT '最后更新人用户ID，未记录时为空',
  `update_time` DATETIME DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP COMMENT '最后更新时间',
  `is_deleted` TINYINT NOT NULL DEFAULT 0 COMMENT '逻辑删除标记：0=已绑定，1=已解绑',
  -- 应用生成的关联唯一标识。
  PRIMARY KEY (`id`),
  -- 包含已解绑记录也唯一，重新绑定恢复该记录，避免软删除后唯一键冲突。
  UNIQUE KEY `uk_device_expense_expense` (`expense_id`),
  -- 按用户查询设备的有效支出关联。
  KEY `idx_device_expense_user_device` (`user_id`, `device_id`, `is_deleted`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_unicode_ci COMMENT='设备支出关联表';
```
