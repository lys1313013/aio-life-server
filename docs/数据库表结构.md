# AIO Life 数据库表结构

当前仅支持 PostgreSQL 18+。本页描述 `sql/migrations/V20261110_01__postgresql_schema.sql` 叠加后续增量定义的当前 68 张业务表（当前至 `V20261113_01`）；公共初始数据由 `V20261110_02_001` 至 `V20261110_02_011` 按用途分别维护，文件与顺序见 [SQL 入口](../sql/README.md)。旧库结构、数据和历史修正 SQL 均已清理，仅通过 Git 历史追溯。

跨表业务语义见[数据库设计审查与字段规范](数据库设计审查与字段规范.md)，执行、预检与离线搬迁见[数据库初始化与验证](数据库初始化与验证.md)。结构变更新增更高版本 V 并同步本文、实体与调用方；已执行迁移不可改写。

- ID 由应用生成，接口始终输出字符串；逻辑删除保持数字 0/1。
- 本地时间使用 timestamp without time zone；JSON 使用 jsonb；二进制使用 bytea；精确数值使用 numeric。
- 普通业务文本使用数据库默认排序规则（确定性、精确比较）；大小写不敏感只在查询层用 `ILIKE` 或 `lower()` 显式表达。API Key、BV 号、对象键、外部订单号等外部标识，以及菜单路径、配置键、字典类型/键值、导出幂等键、平台/人格/任务/地区编码等机器标识使用确定性 `COLLATE "C"`；正则检查显式使用确定性排序。
- 审计更新由实体/Mapper 显式维护，数据库不隐式执行 ON UPDATE。
- 下表必填表示数据库 NOT NULL，接口必填以有效 DTO 校验为准。Flyway 账本与 migration_archive 为基础设施，不映射业务实体。

- `sys_user_uk_user_wechat_active`：唯一性约束：uk_user_wechat_active；`CREATE UNIQUE INDEX sys_user_uk_user_wechat_active ON public."sys_user" USING btree (wechat_openid, active_flag)`。

- `sys_user_uk_user_username_active`：唯一性约束：有效用户名唯一，已删除用户不占用；`CREATE UNIQUE INDEX sys_user_uk_user_username_active ON public."sys_user" USING btree (username) WHERE (is_deleted = 0)`。

约束：

- `ck_sys_user_phone_pair`：`CHECK ((((phone_country_code IS NULL) AND (phone IS NULL)) OR ((phone_country_code IS NOT NULL) AND (phone IS NOT NULL) AND regexp_like(((phone_country_code)::text COLLATE "C"), '^[1-9][0-9]{0,2}$'::text) AND regexp_like(((phone)::text COLLATE "C"), '^[0-9]{4,14}$'::text) AND ((char_length((phone_country_code)::text) + char_length((phone)::text)) <= 15))))`。

当前结构不包含外键；`avatar_file_id` 的引用有效性由应用层 `UserAvatarFileService.validateForBinding` 校验。

### 审计字段与字典启用状态

- `create_time` / `update_time`：所有业务表使用 `NOT NULL DEFAULT CURRENT_TIMESTAMP`。日志表的事件时间仍使用 `login_log.created_at`、`sys_scheduled_job_log.start_time/end_time` 等独立列。
- `sys_dict_type.is_enabled` / `sys_dict_data.is_enabled`：`NOT NULL DEFAULT 1`，并增加 `CHECK (is_enabled IN (0,1))`；历史 NULL 按启用处理。
- `user_dict_data.is_enabled`：保持可空，`NULL` 表示未设置并继承公共值；增加 `CHECK (is_enabled IS NULL OR is_enabled IN (0,1))`。

### JSON 列类型

纯 JSON 配置列统一为 `jsonb`。

- `goal.progress_variables`、`goal.progress_variable_bindings`、`data_export_job.summary_json`：类型为 `jsonb`，只接受 JSON 对象，空白字符串按未设置转为 `NULL`。
- `data_export_job.scope_json`：保持 `text`。该列按写入字节参与导出请求的幂等哈希（`ExportJobService` 与 `ExportScope.hash` 比较），改为 `jsonb` 会因 PostgreSQL 重排空白和键顺序导致哈希不一致。
- 目标保存时的配置变更判断按 JSON 语义比较，不依赖数据库读回的规范化文本与客户端原文逐字节相等。

### 文本排序规则与大小写

所有文本列使用数据库默认的确定性排序规则，按字节精确比较；大小写、重音和全半角不同的值不相等。大小写不敏感只在查询层显式表达：模糊匹配使用 `ILIKE`，等值匹配使用 `lower(col) = lower(?)`。`sys_user.username`、`sys_user.email` 的有效记录唯一索引基于 `lower(col)`，登录、注册查重和找回密码使用相同表达式。

以下机器标识显式使用 `COLLATE "C"`，保证与数据库 locale 无关的固定字节序：

- `sys_menu.path`
- `sys_config.config_key`
- `sys_dict_type.dict_type`、`sys_dict_data.dict_type`、`sys_dict_data.dict_value`
- `user_dict_data.dict_type`、`user_dict_data.dict_value`
- `data_export_job.request_key`
- `membership_provider.code`
- `cbti_personality.code`
- `sys_scheduled_job.job_code`
- `sys_region.code`、`sys_region.parent_code`

数据库默认排序规则由建库参数决定（PostgreSQL 18 默认 builtin `C.UTF-8`），不承诺中文拼音序；需要拼音序的查询显式写 `COLLATE "zh-x-icu"`。修改列排序规则会重建相关索引。
